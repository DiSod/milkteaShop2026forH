## 1. 🔧 拟第 6 周调整

### 1.1 ⭐ 完整性缺口与取舍评估

#### 问题 1：券的核销时间没有落在有效期内

| 项 | 内容 |
|---|---|
| **问题** | `ck_coupon_valid_period` 只保证 `valid_to > valid_from`，**没有任何约束保证 `used_time` 落在 `[valid_from, valid_to]` 内** |
| **业务证据** | 课程第 5 周提示「**请区分数据库现有约束与业务要求**」。业务上「过期券不能核销」是硬规则；但库里可以写出一张「过期后 3 天才核销」的券 |
| **影响** | 中等。积分/券是 v0.1 的评分点之一（`vk_points_ledger_target` 刚在 ISSUE-008 修过），此处是同类漏洞的**剩余缺口** |
| **改进方向** | 补 `CHECK (used_time IS NULL OR (used_time >= valid_from AND used_time <= valid_to))`。⚠️ 需同时确认造数数据全部满足，否则迁移会失败 |
| **本轮验证** | ✅ 已实测 `constraints.sql` 该约束确实只含 `valid_to > valid_from` |
| **成本** | **低**（1 条 `CHECK` + 回归测试） |

#### 问题 2：明细 `subtotal` 与 `qty × unit_price` 的一致性未约束（已实测确认：否决单表 CHECK）

| 项 | 内容 |
|---|---|
| **问题** | `tbl_order_detail` 有 `qty` / `unit_price` / `subtotal` 三个字段，**但没有 `CHECK` 保证 `subtotal = qty × unit_price`** |
| **业务证据** | 金额一致性是收银系统的底线。目前仅靠应用层计算写入 |
| **影响** | 中等。金额错账在答辩演示（对账查询）时会直接暴露 |
| **实测确认** | ✅ **工程侧实测结果**：在全库 2,630 行明细中，**615 行（加料订单）的 `subtotal != qty * unit_price`**（最大差额 3.00）。进一步关联加料表 `tbl_order_detail_topping` 检验公式：`subtotal = (qty * unit_price) + Σ(topping_qty * topping_unit_price)`，实测 **2,630 行 100% 严格吻合，0 差额**！证明业务上**小料加价已计入 `subtotal`**。 |
| **裁决结论** | ❌ **坚决否决**在 `tbl_order_detail` 添加行级 `CHECK (subtotal = qty * unit_price)`（该约束一旦添加将导致 615 行合法明细报错阻断）。 |
| **改进方向** | 该规则属于跨表派生一致性，无法由单表行级 CHECK 保证。**转为第 6 周（ch7）规范化分析中的论证素材**（分析“派生属性冗余 vs 一致性维护成本”的反规范化取舍）；后续阶段三可通过触发器/存储过程或应用层事务保障。 |
| **成本** | **零（维持现状并做论证）**，已闭环（见 ISSUE-011） |

#### 问题 3：券「只能核销一次」是状态转换约束，库里没有

| 项 | 内容 |
|---|---|
| **问题** | `ck_coupon_status` 保证 `status` 取值合法，但**不保证状态只能单向转换一次**（`UNUSED → USED` 不可逆） |
| **业务证据** | 券被重复核销＝直接资损 |
| **影响** | 中高。属**资损类**风险，优先级高于前两条 |
| **改进方向** | 标准 SQL 无法用 `CHECK` 表达状态机；需 **触发器** 或把核销封装进事务型存储过程。**这两者都属第 11—12 周（阶段三）的课程内容** |
| **建议** | ⚠️ **第 6 周先记为「已知缺口」**，标注「需阶段三程序对象才能彻底解决」——**不要为了第 6 周而提前引入触发器** |
| **成本** | **高**（跨阶段） |

### 1.2 需权衡（1 条）

#### 问题 4：`tbl_stock_ledger` 的「多态来源」是否算范式问题

| 项 | 内容 |
|---|---|
| **问题** | 「来源」用**判别列 `ref_type` + 3 个真外键**（`purchase_order_id` / `order_id` / 隐式 `OPENING`）表达 |
| **业务证据** | D-09 决策：**不用字符串 `ref_no`，改用真外键** —— 这样每个来源都被数据库强制保证存在 |
| **影响** | **正面**：消除了弱类型引用（30 个外码里**没有一个是弱类型**）<br>**存疑**：多个可空外码 + 判别列，属「可讨论的范式问题」 |
| **两个方向** | **① 保留**：代价是多列可空，收益是引用完整性硬保证<br>**② 拆分**：按来源拆成 3 张子表 → 引入多表连接，**可读性与查询成本变差** |
| **倾向** | **保留现状**，但在第 6 周规范化分析里**作为「反规范化取舍」案例正式记录理由** |
| **成本** | 若拆分则**高**；保留则**零** |

> 📌 本项**不建议随第 6 周的迁移脚本一起动手** —— 它是同周（ch7 函数依赖与规范化）**分析章节**的素材，
> 结论应落在 `normalization.md` 的反规范化论证里，**而不是体现在 DDL 变更上**。

## 2. 🛡 保留：有意的设计取舍（答辩必答）

> 课程第 5 周原文：「**设计合理的部分写明保留理由**」。

| # | 设计 | 保留理由 | 答辩话术 |
|---|---|---|---|
| 1 | **`tbl_recipe` 用 `sugar_spec_id IS NULL` 表达「与糖度无关」** | 若为「无关」造一个糖度档，会污染 DOM-12 的域语义（`NONE` 是「无糖」这一**真实档位**，不是「不适用」）。**用 `NULL` 表达「该维度不参与」是标准做法** | 「『无糖』和『与糖度无关』是**两回事** —— 前者是一个糖度档，后者是**这一行不受糖度维度约束**」 |
| 2 | **所有主码用代理键**（D-04） | 业务码可能变更（工号、手机号）；代理键让外码与业务码解耦 | 「每张表都能现场举出 **候选码** —— 代理键是选出来做标识的，候选码是其他也能唯一标识的」 |
| 3 | **`tbl_member.points_balance` 冗余存积分余额**（D-12） | 每次查余额都聚合流水代价高；余额是**高频读取**字段 | 「这是**有意的反规范化**，一致性由事务维护；第 6 周会对它做正式的取舍论证」 |
| 4 | **下架用 `product_status` 状态位，不删行** | 历史订单必须能追溯到商品；删行会破坏引用完整性 | 「删了商品，历史订单的明细就成了悬空引用 —— 我们**改状态**」 |
| 5 | **员工离职用 `is_active = 0`，不删行** | 同上，历史流水的 `operator_id` 必须有效 | 同 4 |
| 6 | **`tbl_ingredient` 三表合一**（字典 + 库存 + 采购策略） | 单店场景下三者**一对一**，拆表只增加连接成本 | 「只有进多门店/多库位时，这个合并才会变成问题 —— 而我们的边界是**单店**」 |
