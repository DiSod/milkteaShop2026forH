## 2. 顾客视角：点单

### 2.1 记住一句话：**登录即会员**

本系统**没有游客态**。能登录的人，登录那一刻就是会员；积分、订单都记在这个人名下。

> 库里 `tbl_order_header.member_id` 允许为空——那是为了容纳 v0.1 的 764 张历史散客单（38.9%），
> 不是给新客人留的口子。新单必须绑会员；只有收银台代客下单时才会出现 `member_id` 空值。

### 2.2 点一杯

1. 打开 `/`，页面按**分类**分组显示饮品卡（水果茶 / 经典奶茶 / 纯茶 / 冰淇淋与奶昔 / 季节限定）；
2. **点一张卡片** → 弹出定制窗口：杯型（带价）、糖度、冰量、数量（0—5）、加料（可多选）；
3. 窗口底部实时显示小计 = `(杯价 + 加料价) × 数量`；
4. 点「加入订单」→ 卡片显示「已选 N 杯」，页面底部出现**悬浮价格栏**（`N 杯 · ¥合计`）；
5. 点悬浮栏 → 购物车抽屉：可 `−` / `+` / 改（重新打开该饮品窗口）/ 清空；
6. 点「提交订单」→ 回到「我的订单」，看到进行中的单与取餐号。

**做不了的情况（显示「售罄」）**

| 情况 | 表现 |
|---|---|
| 某杯型的原料沽清 | 该杯型在下拉里**灰掉**并标「（售罄）」，其余杯型仍可选 |
| 该饮品所有杯型都做不了 | 归入页面底部「今日售罄」，卡片不可点 |

> 数量默认是 0：只选杯型不选数量，这张卡不会进单。点「加入订单」时会自动补 1 杯。

### 2.3 看订单与积分

| 页面 | 内容 |
|---|---|
| `/orders` | **进行中**订单在主表格（含状态与一句人话提示）；**历史订单**折叠在下方，点开才展开 |
| `/me` | 当前积分、会员码、最近积分流水、最近 5 笔订单 |

订单状态与含义：

| 状态 | 中文 | 意思 |
|---|---|---|
| `PENDING` | 待制作 | 已下单待接单 |
| `MAKING` | 制作中 | 制作员已接单 |
| `READY` | 待取餐 | 做好了，等取 |
| `COMPLETED` | 已完成 | 已取餐 |
| `CANCELLED` | 已取消 | 取消（库存**不回冲**） |
| `ABANDONED` | 已弃单 | 弃单（库存**照常耗用**） |

## 3. 收银员：代客下单

`/cashier` 与顾客菜单**是同一套卡片**，只多一个「会员手机号」输入框：

| 输入 | 结果 |
|---|---|
| 留空 | **散客单**：`member_id` 为空，**不产生积分** |
| 填正确手机号 | 记在该会员名下并累计积分（1 元 = 1 分） |
| 填错/不存在的号码 | 400，提示「没有找到该手机号对应的会员；散客请把手机号留空」 |

> 收银员**不能**维护商品、**不能**碰库存（数据库授权就不给）；下单时的扣料走应用的服务端写路径。

## 4. 制作员：制作台

`/maker` 两块：

| 区块 | 内容 |
|---|---|
| 待处理订单 | 单号、取餐号、状态、实付、下单时间；每行一个「推到下一状态」按钮（`PENDING → MAKING → READY`） |
| 需要关注（N 个饮品） | **只列做不出来的**：每行一个饮品，**杯型作列**，末列是状态徽章 |
| 全部饮品可做量（折叠） | 29 个饮品 × 各杯型，点开才展开 |

**看数字的两个约定**

1. 状态徽章：`充足在售`（绿）/ `紧张预警`（黄）/ `临时沽清`（红）；
2. 某格显示「原料沽清」时**不给数字** —— 那个数字是"原料够的话能做几杯"，做不出来，给了会误导。

## 5. 库管员：收货与报损

`/stocker` 三块：

| 区块 | 用途 |
|---|---|
| 待收货采购明细（5 条） | 每行填「本次收货」数量 → 点「收货」。**超收会被拒**（409）；该采购单最后一条收满后自动置 `ACCEPTED` |
| 低于补货点的原料（5 条） | 只看需要补的：`严重不足`（红）/ `触及补货点`（黄）/ `人工沽清`（灰） |
| 库存查询与报损（折叠，60 种） | 按「需处理程度」排序（停用 → 手工沽清 → 低于补货点 → 正常）。每行可填数量 + **原因（必填）** → 点「报损」 |

**两条硬规则**

1. **任何数量变化都会写一条流水**（`tbl_stock_ledger`），库里 `qty_on_hand` 必须等于流水之和；
2. 报损数量必须为正、不能超过结存、**必须填原因**；报损写 `LOSS` + `MANUAL`。

> **不提供的操作**：盘点（`STOCKTAKE`）是明确延后到第 13 周的事，这里没有假入口；
> 也不能直接改 `qty_on_hand` —— 改数量只能通过收货/报损，这样流水才闭合。

## 6. 店长：报表与商品维护

`/manager` 四块：

| 区块 | 内容 |
|---|---|
| 近 7 天趋势 | 柱 = 实收（左轴），线 = 订单数（右轴）。**只列有订单的营业日**；中间断档会插一个浅色占位标签（如 `09-24~11-07`）并断线，避免把"没数据"读成"跌到 0" |
| 销量 Top 10 | 横向柱，口径 **D**（仅 `pay_status='SUCCESS'`） |
| 最近 7 天经营日报 | 营业日 / 订单 / 完成 / 取消 / 杯数 / 毛销售 / 折扣 / 实收 / 会员单 |
| 商品档案（30 个） | 每行可直接改名称、单价、状态（在售 / 下架）→ 「保存」；「下架」是删除的等价物 |

**为什么"删"是"下架"**：`tbl_order_detail.product_id` 有外键，硬删会让历史订单失去引用。
所以商品只下架，历史订单照常可查。

**商品维护只有店长能做**：数据库授权里 `role_cashier` 对 `tbl_product` 只有 `SELECT`。

## 7. 报错怎么看

页面上的错误都按**同一套格式**显示：错误码 + 一句中文 + 请求标识（`request_id`，可在服务端日志里定位）。

| HTTP | 错误码 | 含义 | 常见触发 |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | 参数不合法 | 数量 0 或超 20、单价为负、报损没填原因 |
| 401 / 302 | `UNAUTHENTICATED` | 未登录 | 直接访问 `/orders` |
| 403 | `PERMISSION_DENIED` | 岗位无权 | 库管员访问 `/manager` |
| 404 | `NOT_FOUND` | 页面不存在 | 拼错地址 |
| 405 | `METHOD_NOT_ALLOWED` | 方法不对 | 用 GET 打开只接受 POST 的 `/order` |
| 409 | `BUSINESS_RULE_VIOLATION` / `CONSTRAINT_CONFLICT` | 业务规则或数据库约束拒绝 | 重复下架、超收、报损超结存、一券多单 |
| 500 | `INTERNAL_ERROR` | 未预期异常 | 真的出 bug 了，凭 `request_id` 查日志 |

> 数据库的 `Msg 2627`（唯一约束）与 `Msg 547`（外键 / CHECK）会被翻译成 **409**，不会裸露成 500。

## 8. 统计口径（**容易读错，务必先看**）

| 口径 | 定义 | 用途 |
|---|---|---|
| **D（主口径）** | `pay_status='SUCCESS'` **且** `order_status <> 'CANCELLED'` 的 `SUM(amount_paid)` | 系统里所有"销售额"都用它（取消单已退款，不计入） |
| A | 全量 `SUM(amount_paid)` | 对照用，含 `FAILED`（已退款） |
| B | 仅 `order_status='COMPLETED'` | 对照用，不含进行中 |
| 净收入 | `vw_daily_business_summary.net_revenue` | 该视图**无 WHERE**，含 446 元退款，**不是 D 口径** |

其它要记住的：

- **ABANDONED 计入销售额**（钱已经收了）；
- `CANCELLED` 的 `amount_paid` 是**退款前原值**，不是实际收入；
- 三种口径的差额 120.00 元来自折扣。

## 9. 这个系统**不提供**什么

| 不做的事 | 原因 |
|---|---|
| 会员注册 / 开卡 | 登录即会员，没有游客态（A12） |
| 顾客改单 / 删单 | 顾客只有"查 + 增"；业务数据不做物理删 |
| 订单取消与退款流程 | 属第 11—12 周 |
| 盘点（`STOCKTAKE`） | 第 13 周 |
| 行级数据隔离 | 表级授权数据库会真查，行级只能靠应用 `WHERE`（登记为 P-3） |
| 会员查看积分流水 | `role_cashier` 没有 `tbl_points_ledger` 的授权，页面会显示"当前数据库身份没有查询权限"的提示（已知边界） |
| 并发抢库存的严格防护 | 下单是"先查后扣"，未加 `UPDLOCK`/序列化（第 11—12 周用存储过程解决） |

## 10. 出问题了先查这三处

| 现象 | 先查 |
|---|---|
| 页面全是"暂无数据" | `/health` 是否 200、`tables` 是否 18 |
| 中文乱码 / 数据没进去 | `.sql` 是否 **UTF-8 带 BOM**、`sqlcmd` 是否带 `-f 65001` |
| 改了模板没生效 | Flask 非 debug 模式会**缓存 Jinja 模板** —— 重启进程；改 CSS/JS 不用重启 |
| 回归变红 | `regression.sql` 只断言**种子区间**（`business_date < '2026-10-01'`），运行期新增订单不参与断言；若断言红，先看它打印的实际值 |
