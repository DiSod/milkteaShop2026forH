## 一、权限设计的两处取舍（第 4 周）

### 1.1 制作员：用**视图**读库存，而不是直接读表

| | |
|---|---|
| **week1 §2.2 原文** | 制作员**只读**库存、库管员**可写** |
| **实际实现** | `role_maker` 对 `tbl_ingredient` **零直接权限**，只能通过 `vw_product_stock_availability` 读"还能做几杯" |
| **为什么这样更好** | 视图**只暴露"还能做几杯"**，不暴露 `moving_avg_cost`（成本）、`reorder_point`（补货点）等敏感列 —— **用视图代替直接读表，是更细粒度的授权** |
| **定性** | ✅ **有意的收紧，不是遗漏** |

**实测验证：**

```sql
EXECUTE AS USER = 'usr_test_maker';
SELECT COUNT(*) FROM tbl_ingredient;               -- ❌ 拒绝 SELECT 权限
SELECT TOP 1 * FROM vw_product_stock_availability; -- ✅ 通过（57 行）
REVERT;
```

> ⚠️ **说法要准确**：week1 那条"制作员只读库存"**没有被字面落实**，
> 而是**被替换成了更受控的读路径**（视图）。答辩时这么讲，比说"给了只读权限"更站得住。

### 1.2 ⭐ 已知边界：跨岗位的业务动作，**纯 RBAC 无解**

#### 问题：点一次「下单」，数据库里发生了什么

收银员点了**一个按钮**。但这个按钮在数据库里触发的是**6 个动作**：

```
点击「下单」
   │
   ├─ ① 写订单头        INSERT  tbl_order_header            ┐
   ├─ ② 写订单明细      INSERT  tbl_order_detail            ├─ 订单域
   ├─ ③ 写加料          INSERT  tbl_order_detail_topping    ┘   （role_cashier）
   │
   ├─ ④ 查这杯用多少料  SELECT  tbl_recipe                     配方
   │
   ├─ ⑤ 写库存流水      INSERT  tbl_stock_ledger            ┐
   └─ ⑥ 扣减库存        UPDATE  tbl_ingredient              ┘  库存域
                                                              （role_stocker）
```

**对用户来说是「一个动作」；对数据库来说是「跨了两个域的一串动作」。**

#### SQL Server 是怎么判权限的

```
你要执行  INSERT tbl_stock_ledger
        ↓
SQL Server 查：当前身份对这张表有 INSERT 权限吗？
        ↓
  没有 → 拒绝（Error 229）
```

**它不知道、也不关心：**
- 步骤 ⑤ 是因为步骤 ① 才发生的
- 这杯奶茶是"小张的单"
- 这是"业务上的一个动作"

**它只知道：你要写一张你没权限的表。**

#### 矛盾在哪 —— **两个设计目标打架**

| 目标 | 出处 | 要求 |
|---|---|---|
| **A. 岗位制衡** | week1 §2.2 第三组职责分离 | **任何人不能同时握有订单域和库存域** |
| **B. 反冲倒扣** | 裁决 **D1** | **下单必须同时扣库存** |

**A 要求把两个域分开；B 要求一个动作同时写两个域。**

第三组分离做到了极致 —— 分得干干净净，**但这恰恰让 B 无法执行**。

```
role_cashier（收银员）  ─── 管订单和钱
role_stocker（库管员）  ─── 管库存和料
        ↑
   两个域被刻意隔开，好互相制衡
        ↓
   但"下单一笔"需要同时写两边  ✗
```

#### 实测现象

```
EXECUTE AS USER = 'usr_test_cashier';

INSERT INTO tbl_order_header ...   →  ✅ 成功（收银员有权限）
INSERT INTO tbl_stock_ledger ...   →  ❌ 拒绝 INSERT 权限
UPDATE     tbl_ingredient ...      →  ❌ 拒绝 SELECT 权限
```

| 角色 | 能下单 | 能写库存流水 | 能扣库存 |
|---|---|---|---|
| `role_cashier` | ✅ | ❌ | ❌ |
| `role_stocker` | ❌ | ✅ | ✅ |

#### 为什么**不能**简单地"给收银员库存权限"

```sql
GRANT UPDATE ON tbl_ingredient TO role_cashier;   -- ← 千万不能这么干
```

**给了之后：**
- 收银员**既能开单、又能改库存** → **第三组分离当场作废**
- 更糟：他**可以不通过订单直接改库存数字**

```
有权限前：收银员扣料   →  必须走订单 → 按配方扣        →  有据可查
有权限后：收银员改库存 →  UPDATE tbl_ingredient SET qty=0  →  😱 凭空改，不留痕
```

> **权限给的是"对整张表的操作权"，不是"通过某个业务动作的操作权"。** 这是关键。

#### 正解：把「流程」本身变成有权力的主体

**类比 —— 公司报销：**

| | 谁能做 |
|---|---|
| **员工** | 能**提交**报销单 |
| **出纳** | 能**从公司账户付款** |
| **员工能自己转账吗** | ❌ **绝对不能** |

报销怎么完成？—— **走流程**。员工提交 → 系统按规则生成付款指令 → 出纳（或系统）执行。

**没有人因为"员工提交了报销"就给他转账权限。而是「流程」本身有权限。**

**落到 SQL Server：存储过程 + `EXECUTE AS OWNER`**

```sql
CREATE PROCEDURE sp_create_order
    @product_id INT, @qty INT, ...
WITH EXECUTE AS OWNER        -- ← 关键：执行时"借用"表所有者（dbo）的身份
AS
BEGIN
    INSERT INTO tbl_order_header  ...         -- 步骤 ①②③
    INSERT INTO tbl_stock_ledger  ...         -- 步骤 ⑤  ← 以 dbo 身份，写得进去
    UPDATE tbl_ingredient SET qty_on_hand ... -- 步骤 ⑥
END
```

然后**只给收银员"执行权"，不给表的写权限**：

```sql
GRANT EXECUTE ON sp_create_order TO role_cashier;   -- 只有这一条
```

**效果对比：**

| | 直接写表 | 执行存储过程 |
|---|---|---|
| 收银员对 `tbl_stock_ledger` | ❌ 没有任何权限 | ❌ **仍然没有任何权限** |
| 收银员对 `sp_create_order` | — | ✅ 有 `EXECUTE` |
| 存储过程内部（以 dbo 身份） | — | ✅ 写得进去 |

```
收银员 ──EXECUTE──► sp_create_order ──(以 dbo 身份)──► 写订单 + 扣库存
   │                      ↑
   └── 对库存两张表：依然【零权限】
```

> **权限边界保留，业务动作却能完成。**
> 收银员能"下单"，但依然**不能凭空改库存** —— 因为他只能走存储过程，
> 而存储过程**只按配方扣、且必须对应一张真实订单**。**制衡还在。**

**顺带收益**：存储过程里可以把收银员的 `employee_id` 写进流水的 `operator_id`，
比现在"`NULL` = 系统自动"更有据可查。

#### 为什么留到第 11—12 周

| 周 | 学什么 | 解决什么 |
|---|---|---|
| **第 4 周**（已完成） | 角色与授权 | **静态**：谁能读 / 写哪张表 |
| **第 11—12 周** | 存储过程 / 触发器 | **动态**：跨岗位的业务动作怎么安全执行 |

用到的 `CREATE PROCEDURE`、`EXECUTE AS`、**所有权链（ownership chaining）**
**全都是第 11—12 周的内容** —— 现在**还没学到工具**，所以不是"没做"，是"还没到"。

#### 附：这个"做不到"其实是**好消息** 🎯

**它恰恰证明第三组职责分离是真的生效了，不是写在文档里的空话。**

答辩时可以这么讲：

> "我们把订单域和库存域按岗位分开授权，实测发现 —— **收银员开单时连扣料都做不到**。
> 这正是分离生效的证据。
> 当然真实系统不能让收银台停摆，所以第 11—12 周我们会用**存储过程 + `EXECUTE AS OWNER`**
> 把'开单 + 扣料'封成一个受控入口 —— **权限边界不放松，业务动作能完成**。"

**这比"我们的权限设计很完善"有说服力得多** —— 因为它展示了**你发现了设计的边界**。
