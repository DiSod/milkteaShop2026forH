# baseline · 迁移前基线快照

课程第 6 周任务 ① 要求「**保存 v0.1 数据副本 + 订单明细、商品销售统计、库存查询的迁移前结果**作为对比基准」。
本目录就是这三份基准。

**快照不是回归测试。** 分工如下：

| | 基线快照（本目录） | `regression.sql`（待写） |
|---|---|---|
| 服务对象 | 人：看迁移前后到底变了什么 | 机器：一眼判定"还对不对" |
| 输出 | 完整查询结果 + 行数 + 指纹 | 断言 → 通过 / 失败 |
| 会不会失败 | 不会（只 SELECT） | 会（`THROW` + 非零退出码） |
| 时机 | 迁移**前**先跑一遍存档 | 迁移**后**以及日后每次改模式都跑 |

串法：先用本目录的脚本存下迁移前结果，把其中关键数字固化成 `regression.sql` 的期望值，
迁移后再跑同一套脚本，**先比指纹、再比明细**。

## 一、三个脚本

| 脚本 | 覆盖课程场景 | 查什么 | 结果文件 |
|---|---|---|---|
| [`01-order-detail.sql`](01-order-detail.sql) | 订单明细 | 分层抽样的 34 张订单的逐行明细，附复算小计与偏差 | [`result/before-S01.txt`](result/before-S01.txt) |
| [`02-product-sales.sql`](02-product-sales.sql) | 商品销售统计 | 按商品 × 三种销售额口径；订单级口径对照；差额归因 | [`result/before-S02.txt`](result/before-S02.txt) |
| [`03-stock-query.sql`](03-stock-query.sql) | 库存查询 | 原料基表逐行 + 按单位分组 + 库存视图逐行 | [`result/before-S03.txt`](result/before-S03.txt) |

**为什么库存要同时查基表和视图**：迁移改的是基表。只查视图会把"视图 vs 视图"的差异吸收掉，
视图坏了也可能两边一样；所以 `03` 的 3a 查 `tbl_ingredient` 原始行、3b 查 `vw_product_stock_availability`，
两者各有独立指纹。

## 二、怎么跑

```powershell
cd project\tests\baseline
sqlcmd -S .\SQLEXPRESS -E -C -d milktea_shop -f 65001 -W -s"|" -w 8000 -i 01-order-detail.sql -o result\before-S01.txt
sqlcmd -S .\SQLEXPRESS -E -C -d milktea_shop -f 65001 -W -s"|" -w 8000 -i 02-product-sales.sql -o result\before-S02.txt
sqlcmd -S .\SQLEXPRESS -E -C -d milktea_shop -f 65001 -W -s"|" -w 8000 -i 03-stock-query.sql -o result\before-S03.txt
```

迁移后同样跑一遍，只是把输出名换成 `after-S01.txt` 等，然后：

```powershell
# 先看指纹（最快），再 diff 明细
Compare-Object (Get-Content result\before-S01.txt) (Get-Content result\after-S01.txt)
```

四个参数不是可选的：

- **`-d milktea_shop`** —— 不加会连到 `master`，脚本里有 `USE` 兜底，但输出里会多一行上下文切换提示。
- **`-f 65001`** —— 脚本含中文，codepage 不对就会变问号。
- **`-W`** —— 去掉每行尾部的填充空格。不加的话，一行能撑到几千字符，diff 全是噪声。
- **`-s"|"`** —— 用竖线做列分隔，diff 时才看得出是哪一列变了。

## 三、迁移前实测基线（2026-10-15，`milktea_shop` 全量 20,979 行）

### S1 订单明细

- 抽样：34 张订单 / 59 行明细 / 17 行加料，**指纹 `-1674015621`**
- 覆盖：用券 24 单 41 行 / 多明细 3 单 9 行 / 有加料 4 单 5 行 / 散客 3 单 4 行
- 不变量：`复算小计 = qty × unit_price + Σ加料费`，59 行**偏差全为 0**

> 各层配额是"去重前各取 4 单"，与"用券 24 单"重叠的会被吞掉，所以 A 层净得 3 单、D 层净得 3 单。
> 这是确定性行为，不是抽样 bug。

### S2 商品销售

29 个商品有销售（共 30 个商品，`P030 红丝绒奶昔`已下架且无销售），**指纹 `436093178`**。

| 口径 | 订单数 | 小计合计 | 折扣 | 实付金额 |
|---|---|---|---|---|
| A 全量（不分状态） | 1,963 | 24,328.00 | 120.00 | 24,208.00 |
| **D 已收款（⭐ 主口径）** | **1,926** | **23,882.00** | **120.00** | **23,762.00** |
| B 已完成 | 1,894 | 23,473.00 | 110.00 | 23,363.00 |
| 已退款（由 `FAILED` 反推） | 37 | 446.00 | 0.00 | 446.00 |

三个口径是包含关系 **A ⊃ D ⊃ B**，数字互不相同，都要留档。

D 口径下：杯数 2,579、商品金额 22,389.00 + 加料费 1,493.00 = 小计 23,882.00（偏差 0）。

**两个必须写进报告的差额**：

1. `小计合计 23,882.00 − 实付金额 23,762.00 = 120.00`，恰好等于折扣合计（已完成 110 + 已弃单 10）。
   按明细求和与按订单求和**天生不等**，这个 120 不是 bug。
2. `ABANDONED` 32 单：小计 409.00、折扣 10.00、**实付 399.00**、均价 12.47。
   已付款、已制作、未取件，按裁定**计入销售额**。

## 四、这次建基线踩到的坑（写下来免得下次再踩）

1. **`sale_status` 是中文四值**：`充足在售` / `紧张预警` / `临时沽清` / `已下架`，
   不是 `AVAILABLE` / `SOLD_OUT`。第一版脚本按英文枚举写 `CASE`，结果统计出一片 0，
   差点得出"沽清分支未被数据覆盖"的错结论 —— 实际上沽清有 4 行。
2. **`tbl_order_detail_topping` 的列是 `unit_extra_price`，不是 `unit_price`**。
3. **JOIN 会放大订单头**。把 `tbl_order_header` 和 `tbl_order_detail` 直接 JOIN 后再 `SUM(h.amount_paid)`，
   一张多明细订单会被算多次（实测 `23,762.00` 被放成 `37,387.00`）。两侧必须分别聚合。
4. **`CHECKSUM_AGG` 与行序无关**，适合做快速跳闸；但校验和可能碰撞，**指纹一致仍要抽查明细**。
5. **`.sql` 必须 UTF-8 with BOM**（本项目既有规则）。用脚本改写时注意别把 BOM 剥掉，
   否则 `sqlcmd` 遇到中文会静默出错。
