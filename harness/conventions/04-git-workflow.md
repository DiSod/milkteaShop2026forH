# 04 · Git 协作规范

适用：2—3 人共用同一个仓库。

## 1. 提交信息格式

```
<类型>: <简短描述>

<可选：为什么这么改>
```

### 类型

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat` | 新增功能/脚本 | `feat: 新增订单表 DDL 脚本` |
| `fix` | 修正错误 | `fix: 修正库存流水的错误外键` |
| `sql` | 纯 SQL 脚本变更 | `sql: 补充销售耗用的存储过程` |
| `docs` | 文档 | `docs: 完成第一周业务需求分析报告` |
| `data` | 数据生成/清洗脚本 | `data: 补造 90 天原料台账` |
| `refactor` | 重构（不改行为） | `refactor: 拆分过长的建表脚本` |
| `chore` | 杂项（配置、目录） | `chore: 建立仓库目录骨架` |
| `wip` | 未完成，临时存档 | `wip: 视图设计进行中` |

### 规则

- **描述用中文**（与文档语言一致），**类型用英文**
- 描述写**做了什么**，不写"更新""修改"这类无信息量的词
- 一次提交只做一件事

### 反例

| ❌ 不好的提交 | ✅ 改成 |
|---|---|
| `update` | `docs: 补充第二周数据边界清单` |
| `修改` | `sql: 修正订单明细的外键级联规则` |
| `111` | `chore: 建立仓库目录骨架` |
| `feat: 建表、写查询、改文档、加数据` | 拆成 4 次提交 |

## 2. 分支策略

小组规模小（2—3 人），采用**轻量分支**：

```
main                ← 始终可运行、可交付
 └─ feat/<主题>      ← 单人短期分支，完成后合并回 main
```

| 分支 | 规则 |
|---|---|
| `main` | **必须保持"从空库可一键重建"**。合并前必须本地验证。`harness/issues/` 的提报统一在 `main` 沉淀 |
| `feat/<主题>` / `fix/<issue-id>` | 单人短期分支，命名如 `feat/week03-ddl`、`fix/issue-003` |

### 合并与同步规则

1. **开工同步**：开发分支每次开工前，先执行 `git pull --rebase origin main` 同步最新 Issue 与公共规范；若不便变基，可通过 `git show origin/main:harness/issues/` 跨分支巡检待办。
2. **Issue 闭环**：代码或文档修复分支在本地验证通过后，将对应 Issue 文件标记为 `🟢 已解决`，随分支一同合入 `main`。
3. **合并前验证**：合并前**必须先跑通 `project/sql/99-rebuild.sql`**。
4. **合并策略**：合并时用 **squash**（保持 `main` 历史线性可读）。
5. **代码防冲撞**：业务代码开发走分支，**不要**直接在 `main` 上开发未经验证的 SQL 代码。

### 2.1 什么走分支、什么直接进 `main`

> 定于 2026-09-23。**判定按文件路径，不按内容** —— 避免"这算文档还是代码"的扯皮。
> 起因：`project/docs/data-dictionary.md` 是设计文档但位于 `project/` 下，按第 5 条会被误判为需要分支。

| 路径 | 归类 | 走哪 |
|---|---|---|
| `project/sql/**` | **代码** | 分支（`feat/` 或 `fix/`） |
| `project/app/**`、`project/tests/**` | **代码** | 分支 |
| `project/data/**/*.py`（造数脚本） | **代码** | 分支 |
| **`project/docs/**`** | **文档** | ✅ **直接进 `main`** |
| `harness/**`（规范 / 看板 / 团队） | **文档** | ✅ 直接进 `main` |
| `weeks/**`（周报与过程材料） | **文档** | ✅ 直接进 `main` |
| 根 `README.md`、`STRUCTURE.md` | **文档** | ✅ 直接进 `main` |

**关键裁定：设计文档不算代码。**
`project/docs/` 下的设计文档（数据字典、ER 图、范式分析、迁移说明）**直接进 `main`**，
不需要开分支，也不适用"跑通 `99-rebuild.sql`"这条门槛 —— **它是文档，本来也跑不了。**

**分支只为"防代码冲撞"而存在** —— 两人同时改一个 SQL 脚本会冲突；
而文档走的是**单写者**机制（[`team/README.md`](../team/README.md)：文档全权由 DiSod 独占执笔），**从源头就没有并发**。

### 2.2 ⚠️ 过渡期说明（`99-rebuild.sql` 尚未可用）

`project/sql/99-rebuild.sql` 目前**仍是桩文件**（`:r` 调用全被注释，第 3 周才补全），
所以第 3 条"合并前必须先跑通 `99-rebuild.sql`"**当前无法执行**。

**过渡约定**：

| 阶段 | 门槛 |
|---|---|
| 第 3 周首个建表脚本就绪**前** | 文档类改动**不适用**该门槛（本来也不适用）；SQL 类改动**尚无内容可提交** |
| `01-schema/` 有实际内容**之后** | 该门槛**立即生效** —— 任何 SQL 改动必须本地跑通才能合并 |

### 2.3 提交节奏

> 定于 2026-09-23（实践总结）。

- **攒批提交**：不为单个小改动单独提交推送；**按主题攒成一批**（如"第 2 周设计文档全套 + 编号修复"）。
- **但一次提交只做一件事**：一批里的多个 commit 仍应各自聚焦（见第 1 节的类型表）。
- **纯文档改动可以不进 `submissions/`** —— 阶段快照只在**阶段提交节点**做（见第 5 节）。

## 3. 什么不该进仓库

由根目录 `.gitignore` 保证。重点：

| 不该进 | 原因 |
|---|---|
| `project/data/` 下的数据文件 | 单文件达 95MB，GitHub 上限 100MB，且大文件进入历史后无法回落 |
| `*.mdf` / `*.ldf` / `*.bak` | 数据库文件与备份 |
| `harness/logs/raw/` | 原始会话日志体积不可控 |

> 数据靠 `project/data/README.md` 的**下载说明**复现，而不是靠提交文件本身。

## 4. 提交前自检

- [ ] 文件放在**正确的域**？（SQL 在 `project/`、周报在 `weeks/`、规范在 `harness/`）
- [ ] 命名符合 `01-layout-and-naming.md`？
- [ ] 敏感信息？——**数据库密码、服务器地址、个人手机号不要提交**（用占位符或本地配置）
- [ ] 大文件？——单个文件超过 **10MB** 就要停下来想想要不要进 git
- [ ] 跑得通吗？——改了 SQL 就必须跑一遍

## 5. 提交节点

| 时间 | 动作 |
|---|---|
| 每次实验课结束前 | 至少一次提交，`wip` 也可以，**不要攒到最后** |
| 每周结束 | 周报提交 + 本周产出并入 `project/` |
| 阶段提交前 | 从 `project/` 复制快照到 `weeks/submissions/vX.Y/`，该目录归档后不再修改 |
