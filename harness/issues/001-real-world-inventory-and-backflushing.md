## 1. 为什么提这个 Issue？（直白说问题）
目前设计里把库存做成了 **“仓库 ⇄ 操作台移库（双行流水）”**，还试图用 SQL 视图去实时算 **“成品还能做几杯”**。
这严重脱离了真实奶茶店的实际运营逻辑，并且把数据库结构搞得极其臃肿复杂：
- 真实小店的店员根本不可能在从仓库拿两包珍珠到吧台时，去收银机上扫码登记“移库”；
- 真实的奶茶店收银系统也根本不会、且不需要去计算“剩余原料能做 32.5 杯珍珠奶茶”。

---

## 2. 现实奶茶店到底是怎么管库存的？（对齐常识）

现实奶茶店的进销存其实非常清晰简单，分为四步：

1. **料台（前台）—— 人工手动管理 + 依赖沽清**：
   - 前台吧台放什么原料，店员肉眼可见，**不建物理库存表，也不记移库流水**；
   - 某样料用完了（比如没珍珠了），店员在收银机上手工点击 **“珍珠沽清”**；
   - 系统根据原料依赖关系，自动把所有用到珍珠的成品在前端展示为 **“已售罄”**。
2. **仓库（总库）—— 自动反冲倒扣（Backflushing，工业标准）**：
   - 顾客下单付款后，系统根据 `订单明细 × 配方 BOM`，**直接自动反向扣减原料仓库的总库存**；
   - 扣减只发生在统一总库，根本不需要中间移库环节。
3. **闭店打烊 —— 称重剩余与损耗确认**：
   - 晚上闭店打烊时，店长将操作台没用完的半成品（如煮好的珍珠、泡好的茶汤）称重，加上按期盘点，把差异直接记录为 **“打烊报损 / 盘盈亏”**。
4. **功能精简 —— 完全不需要“还能做几杯”**：
   - 既然前台售罄靠人工“点击沽清”，后台扣减靠“自动反冲倒扣”，那么原先设计里那个跨多原料求最小值瓶颈、写法极难、性能极差的“还能做几杯”视图，**在业务上根本不需要，直接取消**！

---

## 3. 带来哪些立竿见影的工程收益？
1. **砍掉虚胖结构**：彻底删掉无外码约束的移库号 `transfer_group_no`、删掉成对出现的“领料出库/入库”双行流水；
2. **简化主码**：库存表主码不再需要 `(原料, 库位)` 复合主码，直接恢复为最标准的 `(原料ID)` 为主码，全库 CRUD 清爽无比；
3. **拔除技术地雷**：直接取消了“成品可制作量”视图在 SQL Server 中跨表求 MIN 瓶颈的性能隐患；
4. **答辩无比自信**：面对老师提问，队友可以理直气壮地讲出：“我们还原了真实餐饮连锁的标准反冲倒扣与手工沽清模型，没有盲目照搬大型仓储制造系统的移库逻辑。”

---

## 4. 建议行动方案
- 在第二周报告中将库存模型修正为：**单店统一原料库存（反冲倒扣） + 依赖性手工沽清标记 + 打烊称重报损**；
- 删去原 D-01（双库位）、D-02（双行移库流水）、D-03（只认操作台扣减）的设计负担。
