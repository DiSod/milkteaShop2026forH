## 1. 现象与矛盾描述

[`project/docs/normalization.md`](../../project/docs/normalization.md) 的**结论摘要（§0）**与**判定明细（§3）**对同一批 17 张表给出了两套互斥的范式统计：

- **§0** 说「标准 BCNF **12 张**」+「有意的反规范化（2NF+）**5 张**」；
- **§3** 的 17 行判定表逐个表判定，实际结果是「**14 张 BCNF + 3 张 2NF**」。

两套数各自都能凑满 17（`12+5` / `14+3`），所以不是漏表，而是**结论段与判定表没有对齐**。

另有一处连带矛盾：§0 同一张表里既写「**3NF 关系 0 张**」，又写「有意的反规范化（**2NF+**）5 张」。
若真有 5 张表不满足 3NF，那「3NF 关系 0 张」这句话就没有意义了（2NF 表的 3NF 判定必然是不满足）；
§0 紧挨着的「决定因素全为超码，**无任何部分依赖与传递依赖**」也与 2NF 结论直接冲突。

### 1. 逐项裁决与口径定案

1. **Q1 裁定：全库统一定为「14 张纯净 BCNF + 3 张工程反规范化（受控派生冗余）」**
   - **理由**：原 §0 出现的数字「5」系初稿混淆了「§4 中列举的 5 个反规范化论证案例」与「因冗余列偏离更高范式的表数」。事实上，案例一（`tbl_recipe` 的 `sugar_spec_id IS NULL`）与案例五（`tbl_ingredient` 的单店 1:1 三表合一）在单表函数依赖自身上**严格满足 BCNF**，属于实体合并与域语义维度的工程取舍，表结构自身并不包含破坏更高范式的依赖。
   - **落地**：§0、§1、§3 统一修正为 **14 纯净 BCNF + 3 工程反规范化（合计 17）**，彻底消除 12+5 与 14+3 的矛盾。

2. **Q2 裁定：完全采纳 DiSod 建议，由「2NF」改称为「BCNF（单表）/ 工程反规范化（受控跨表派生列）」**
   - **学术依据**：在经典关系理论中，2NF 的定义是“每个非主属性完全函数依赖于每一个候选码（无部分依赖）”。在 `tbl_member`（码为单列 `member_id` 等）、`tbl_order_header` 与 `tbl_order_detail` 中，决定因素均为超码，且不存在单表内的传递依赖。因此在单表封闭体系下，它们在形式上**直接满足 BCNF**。
   - **工程定性**：这 3 列的冗余来自于**跨表聚合与多表计算**（$\sum(流水) \to 余额$、$数量 \times 单价 + 加料 \to 小计$），属于应用与物理层面的受控派生列。标为「2NF」在学术答辩时容易被扣概念不清晰；修正为「**BCNF（单表纯函数依赖视角）/ 工程反规范化（受控跨表派生列视角）**」既符合数学严谨性，又解释了工程必要性。

3. **Q3 裁定：自洽性与语言重构**
   - §0 移除容易引起误解的「3NF 关系 0 张」，重构为「严格 3NF 但非 BCNF 关系：0 张」，澄清不存在候选码交叉重叠引起的非主属性传递依赖；
   - 明确全库单表形式体系下 100% 达到 BCNF，3 处跨表派生冗余由事务与阶段三触发器硬性维护。
