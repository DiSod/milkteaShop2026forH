# issues · 团队协作与技术排雷看板

本项目采用 **Agent 原生文件式 Issue 系统**。
用于在舍友二人与各自的 AI Agent 之间建立高效、异步、可追溯的技术交流通道，无需对微观技术细节进行低效的口头传达。

---

## 规则摘要（两句话铁律）
1. **统一在 `main` 追踪**：所有 Issue 直接在 `main` 维护，一 Issue 一文件，避免并发编辑大文件产生 Git 冲突；
2. **开工必对齐，修复随合闭环**：
   - Agent 每次开工前，先读取本看板认领属于自己的待办；
   - 开发分支每次动工前先 `git pull --rebase origin main`；
   - 修复分支在本地跑通 `project/sql/99-rebuild.sql` 后，将对应 Issue 标记为 `🟢 已解决`，合并回 `main` 闭环。

## 闭环怎么写（`## 5. 解决记录`）

> 定于 2026-09-23（首次闭环时总结）。**这一节是"修复随合闭环"的落点，不要省。**

### 结构

| 项 | 要求 |
|---|---|
| **处理人** | 谁做的（人名） |
| **解决时间** | 日期；未定案写 `⏳` |
| **状态** | 一句话说清"**解决了什么 / 还等什么**"，不要只写"已完成" |
| **裁决 / 变更说明** | ⭐ **逐条对照原始诉求**给出结论（采纳 / 否决 / 折中），**并说明理由** |
| **commit 引用** | 至少一条能追溯的 commit |
| **遗留** | 未解决的部分**不要删**，写在这里（`03-documentation.md` §6：抹掉未决问题会变成答辩盲区） |

### 范例

见 [`005-collaboration-and-git-alignment.md`](005-collaboration-and-git-alignment.md) 第 5 节 ——
它按"**三条原则 → 落地位置 → commit 引用 → 遗留**"四段写，是目前最干净的一个。

### 两条经验

**① 标题可能与结论不符 —— 不要改标题**

Issue 是"**提议**"，裁决后标题里的主张**可能被否决**。
**保留原标题**（它是历史记录），但在标题下方加一行 `⚠️ 标题说明` 指明差异。

> 例：ISSUE-001 的标题写着"（取消"还能做几杯"…）"，但裁决后**该视图保留**；
> ISSUE-002 的标题写着"收敛至 10~12 张"，但定案是 **17 张**。

**② Issue 之间的依赖要显式写**

**ISSUE-001（单库 vs 双库）直接决定 ISSUE-002 的表数** —— 两者是同一件事的两面。
各自独立裁决容易出半吊子结果（比如"按 002 精简了表数，表里却还留着库位字段"）。

处理方式二选一：
- **合并讨论**：像第 2 周那样把 001/002/003 写进同一份裁决意见；
- **显式声明**：在元数据里加一行 `| **依赖** | [ISSUE-00X](...) |`。
