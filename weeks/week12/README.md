## 0. 一句话

课程要求「三类窗口查询均有明确业务含义」。我们挑的三类是**累计与环比、分类内排名与占比、
移动平均**——都是店长真的会问的问题，而不是为了演示函数而造的查询。

## 1. 交付了什么

| 文件 | 内容 | 运行 |
|---|---|---|
| [`window_query.sql`](../../project/sql/09-programmability/window_query.sql) | 4 个查询：每日累计 + 环比 / 分类内排名 + 占比 / 近 3 日移动平均 / 三个排名函数口径对照 | `sqlcmd -i project\sql\09-programmability\window_query.sql` |
| [`test-window.sql`](../../project/sql/09-programmability/test-window.sql) | **21 条**断言（预期 / 实际 / PASS｜FAIL），全只读、可反复跑 | `sqlcmd -b -i project\sql\09-programmability\test-window.sql` |

两个脚本都**不进 `99-rebuild.sql`**：它们是查询与断言，不是数据库对象，重建后直接跑即可。

## 2. 为什么这样选（每一类都有业务含义）

| 查询 | 业务问题 | 用到的窗口能力 |
|---|---|---|
| 1 每日累计 + 环比 | “到这一天为止累计多少”“比昨天好还是差” | `SUM() OVER (ORDER BY d ROWS UNBOUNDED PRECEDING)`、`LAG()` |
| 2 分类内排名 + 占比 | “这款在我这一类里第几”“这一类占全店多少” | `RANK() OVER (PARTITION BY 分类)`、`SUM() OVER (PARTITION BY)`、`SUM() OVER ()` |
| 3 近 3 日移动平均 | “单日波动太大，趋势如何” | `AVG() OVER (ORDER BY d ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` |
| 4 排名口径对照 | “并列怎么算第几名” | `ROW_NUMBER` / `RANK` / `DENSE_RANK` 同时算 |

**没有用 `RANGE`**：一天一行时 `ROWS` 与 `RANGE` 等价，但 `ROWS` 在以后改成按小时分组时语义不变，
所以四处都显式写了帧。这条写进了脚本注释——答辩时会被问“默认帧是什么”。

**查询 2** 的关键看得见的事实：

## 4. 21 条断言覆盖了什么

| 类 | 条数 | 典型用例 |
|---|---:|---|
| 累计与环比 | 7 | 行数不增不减、末值 = 合计 = D 口径常量、首日 `LAG` 为 NULL、下跌日保留负号、双过滤等价性 |
| 排名与占比 | 8 | 纯茶/水果茶第一名、96 杯并列、并列后跳号到第 5、每分类一个第 1、分类内合计 100%、全店合计 100%、单款占比 < 100 |
| 移动平均 | 5 | 首日窗口 1 行、09-19 三日均值、09-23 三日合计与均值、均值 ≠ 当日值（口径没被简化） |
| 排名口径对照 | 1 | 并列 90 分时 `RANK 2,2 / DENSE 2,2 / ROW_NUMBER 2,3` |

**测试设计上的三个自我约束**（和 `test-function.sql` 同一套）：

1. 预期值优先**独立重算**（另一条聚合路径算出来再比），只有“业务口径常量”才写死；
2. 用例总数**固定 21**，漏跑判红——不能出现“少一条反而全绿”；
3. 全部只读，不建临时表、不写业务表，随时可重复执行。

写这批时踩到并修掉的两个自己的错：

- **断言 7 原本写“只滤 `pay_status` 会大于双过滤”**，实测相等——因为种子里 37 张取消单的
  `pay_status` 全是 `FAILED`，早被第一条过滤排除了。改成断言“当前数据下两者相等且都等于 23,762.00”，
  并在注释里写明：**一旦出现“取消但支付成功”的单，两者就会分叉**，所以第二个过滤仍然必要。
- **断言 13 原本对全表 `SUM(pct)`**，得到 500（5 个分类各 100）。改成先按分类汇总再断言每个分类
  ≈100%。

## 7. 变异测试：断言是否真的在验（2026-11-25 实测）

做法：复制 	est-window.sql，**故意改坏一处逻辑**再跑，看有没有断言变红。改坏的副本用完即删，仓库里的原文件没动。

| 变异 | 命中处 | 变红的断言 | 判定 |
|---|---:|---|---|
| M1 去掉 PARTITION BY category_name（分类内排名退化成全店排名） | 5 | 8、9、12 | ✅ 抓住 |
| M2 窗口帧 2 PRECEDING 改 1 PRECEDING（三日均值变两日） | 7 | 17、18、19 | ✅ 抓住 |
| M3 LAG 改 LEAD（环比看成“明天”，第一处） | 1 | 4 | ✅ 抓住 |
| M4 LAG 改 LEAD（第二处，usiness_date 版本） | 2 | 5、6 | ✅ 抓住 |

**第一轮跑出一个假通过**：M1 当时只让 8、9 变红，**用例 12 仍然绿** —— 因为它断言的是
COUNT(DISTINCT category_name) = COUNT(*)，去掉分区后只剩 1 行，两个值都等于 1，条件恒真。
已收紧为「第 1 名的行数 = 5（分类数）」，复测后 8、9、12 一起红。

这条经验比结论本身更有用：**“两个数相等”常常是恒真断言**，要再钉一个绝对量（这里钉了 5 个分类）。

变异脚本是一次性工具（harness/logs/tmp-mutation-window.py，未入库），要重跑的话按上表四处替换即可。

## 8. 业务事务：两段 T-SQL 事务脚本（2026-11-25 实测）

课程第 12 周要求「两项事务脚本及提交/回滚结果」。事务我们一直有 —— 但它开在应用层
（project/app/service/ordering.py 的 with db.open_session() as s: … s.commit()），
课上问「事务到底包住了什么」时，代码在 Python 里不好指。这两段把同一件事摊成 T-SQL。

| 脚本 | 干什么 | 结果 |
|---|---|---|
| project/sql/10-transaction/tx1-order-commit.sql | 一次下单：写头 → 写明细 → 扣结存 → 写流水 → 加积分，五步同一个事务 | [COMMIT] 后逐表校验：头 1 行 / 明细 1 行 / 流水 5 行（=原料种类数）/ 积分 1 行；随后自己清理，残留 0/0/0/0 |
| project/sql/10-transaction/tx2-order-rollback.sql | 同一流程，第 4 步故意把结存扣成负数 | 捕获 **547**（撞 ck_ingredient_qty_on_hand）→ 整体 ROLLBACK；六项比对（订单/明细/库存流水/积分流水/会员积分合计/结存合计）全部回到事务前 |

两段都是幂等的：tx1 结尾按 order_id 删掉自己写入的行并按 Σ流水 重算结存，tx2 整体回滚。
连跑一遍，库的七个指标一个都没变：

`
事务前：订单=1963 明细=2629 库存流水=13851 积分流水=1259 积分合计=25224 结存合计=403371.600 结存偏差=0
事务后：订单=1963 明细=2629 库存流水=13851 积分流水=1259 积分合计=25224 结存合计=403371.600 结存偏差=0
`

### 写这两个脚本时踩的两个坑

1. **往 	bl_order_header 写数据必须 SET QUOTED_IDENTIFIER ON**。第一次编译就报
   消息 1934 … INSERT 失败，因为下列 SET 选项的设置不正确: 'QUOTED_IDENTIFIER' ——
   原因是第 9 周建的**筛选索引** uq_order_header_coupon，SQL Server 要求写带筛选索引的表时
   该选项为 ON，而 sqlcmd 默认 OFF。两个脚本开头都显式开了。
2. **配方查询必须带上 sugar_spec_id IS NULL 的行**。只写 
.sugar_spec_id = @sugar_id
   会得到「这个组合没有配方行」——因为基础原料（茶底、水、冰）的用量与糖度无关，
   在 	bl_recipe 里就是 sugar_spec_id IS NULL。正确写法是
   (sugar_spec_id = @sugar_id OR sugar_spec_id IS NULL)，这正是
   order_dao.recipe_usage() 的做法（第 5 周 ER 图 §1.4 登记过这条语义）。

### 和应用层事务的对照

| | 应用层 place_order() | 这两段 T-SQL |
|---|---|---|
| 事务谁开 | pyodbc 连接对象（with db.open_session() as s:） | BEGIN TRANSACTION |
| 提交谁做 | s.commit() | COMMIT TRANSACTION |
| 失败怎么退 | 抛异常 → 上下文管理器 
ollback → REVERT 切回 dbo | TRY/CATCH + XACT_STATE() <> 0 → ROLLBACK |
| 什么时候会发生 | 用户点「提交订单」 | 课上演示 / 批量脚本 |

两条路径的**校验规则是同一条**（原料够不够、配方有没有、金额对不对），区别只在边界由谁管。

## 9. 递归查询：`recursive_query.sql`（2026-11-25 实测）

| 文件 | 内容 | 运行 |
|---|---|---|
| [`recursive_query.sql`](../../project/sql/10-transaction/recursive_query.sql) | R1 日期轴补零 / R2 断档识别 / R3 品类树展开 | `sqlcmd -b -i project\sql\10-transaction\recursive_query.sql` |
| [`test-recursive.sql`](../../project/sql/10-transaction/test-recursive.sql) | **15 条**断言，全只读 | `sqlcmd -b -i project\sql\10-transaction\test-recursive.sql` |

### 为什么这三处要用递归

日期不是表里的数据。库里只有「有订单的那几天」有行，直接 `GROUP BY business_date`，
图就从 09-23 直接跳到 11-08 —— 中间 46 天连行都没有。递归 CTE 先造一把连续的「尺子」
（`SELECT @start UNION ALL SELECT DATEADD(DAY,1,d) WHERE d < @end`），再把事实表 `LEFT JOIN` 上去，
缺的那几天自然得到 0，而不是「消失」。

### 三个查询与实测输出

**R1 日期轴补零**（窗口 `2026-09-17 ~ 09-26`，故意跨过种子最后一天）：

```
2026-09-17|252|3070.00
...
2026-09-23|244|2843.00
2026-09-24|0|.00|无营业
2026-09-25|0|.00|无营业
2026-09-26|0|.00|无营业
```

**R2 断档识别**（gaps & islands）：同一把尺子先标「这天有没有单」，再用
`DATEADD(DAY, -ROW_NUMBER() OVER (ORDER BY d), d)` 把连续段归到同一个常量，按它分组即得区间：

```
空档起|空档止|连续天数
2026-09-24|2026-09-26|3
```

**R3 品类树展开**：沿 `parent_category_id` 递归，带层级与路径（`父 > 子`），并用
「祖先 → 后代」映射做自底向上汇总，算出每个节点**含子级**的销售额。

真实库里 5 个分类的 `parent_category_id` **全是 NULL**（数据还没有层级），所以
`recursive_query.sql` 里这段用**临时表造一棵三级树**：把真实 5 个分类搬进 `#品类`，
再加两个根（`R01 现制茶饮总类`、`R02 甜品与限定总类`）和一个叶子（`S01`），只改临时表的父子关系，
**真表零写入**。实测（2026-11-27）：

```
层级|category_code|category_name|杯数|含子级销售额
1|R01|现制茶饮总类|1862|17063.00
1|R02|甜品与限定总类|717|6819.00
2|C01|水果茶|...|...
3|S01|鲜果茶子类（示例）|...|...
```

`R01 = C01 + C02 + C03` 的直接销售额之和（17,063.00），这就是「递归 + 累加」对上账的证据。
真实数据一旦挂上父级，**这段 SQL 一个字都不用改**就会多出第 2、3 层（临时表那段只是演示用的脚手架）。

### 写的时候踩的三个坑

1. **`date` 不能直接减 `bigint`**：`营业日 - ROW_NUMBER()` 报 `操作数类型冲突: date 与 bigint 不兼容`
   （`ROW_NUMBER()` 返回 bigint）。改成 `DATEADD(DAY, -CAST(ROW_NUMBER() AS INT), 营业日)`。
2. **`COUNT(列名)` 会触发 ANSI 警告**「聚合或其他 SET 操作消除了 Null 值」——
   `LEFT JOIN` 后空档那几天的 `h.order_id` 是 NULL，`COUNT(h.order_id)` 跳过它们就报这句。
   换成 `SUM(CASE WHEN h.order_id IS NULL THEN 0 ELSE 1 END)` 后干净了（`SUM(ISNULL(...))` 同理）。
3. **`sqlcmd` 把 `DECIMAL` 的 0 打印成 `.00`**（不是 `0.00`）——这是 sqlcmd 的单元格格式，不是 SQL 的问题；
   别为了好看去 `CAST` 成字符串，会丢掉数值类型。

### 15 条断言覆盖

行数 = 跨度+1、首末行正确、日期不重复、有营业日 7 天 / 无营业日 3 天、无营业日实收 = 0、
09-18 实收 = 3,074.00（与直接查订单表一致）、**补零后总额仍 = 23,762.00**（不改变业务口径）、
识别出 1 段空档且 = 09-24~09-26 共 3 天、**品类树三级穿透（层级 2/5/1）**、
**根类汇总 = 三个子类直接销售额之和（17,063.00）**、**真表未被临时树污染（5 类 / 父级全 NULL）**、
跨度 > 3660 天被拒（52101）。

> 第 9 条是这组断言里最要紧的：**补零只是「补上没发生的事」，不能让总额变**。
> 它和 `regression.sql` TC-10 的常量 23,762.00 交叉校验，是这条递归唯一的业务锚点。

**这两个脚本不进 `99-rebuild.sql`**：它们是查询与断言，不是数据库对象。
