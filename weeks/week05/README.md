## 六、对新会话的硬性约束（**照做，别自创**）

| # | 约束 | 出处 |
|---|---|---|
| 1 | **禁止同一份内容在两处各自演化** —— 表结构以 `data-dictionary.md` 为准，主数据以 `master-data.md` 为准 | [`01-layout-and-naming.md`](../../harness/conventions/01-layout-and-naming.md) §5 |
| 2 | **含中文的 `.sql` / `.ps1` 必须存为 UTF-8 with BOM** —— 编辑工具会剥掉，**改完必须回补**；否则 `sqlcmd` **静默失效**（无报错、一行不生效） | [`02-sql-style.md`](../../harness/conventions/02-sql-style.md) §9 |
| 3 | **外键命名 `fk_<表>_<列>`** —— 用外键列名，**不用目标表名**（会撞名） | 同上 §3.1 |
| 4 | **严禁对未修改区域做全局重排**（Markdown 表格、行号）—— 会制造 Git 冲突 | [`agent-session-start.md`](../../harness/prompts/agent-session-start.md) |
| 5 | **强断言必须自己实测**，不能只读文档就下结论（`100%` / `全部` / `零差额` 这类） | [`ai-log.md`](../submissions/v0.1/ai-log.md) §3 |

| 7 | **AI 留痕**：影响设计决策的对话、AI 出错被纠正的案例，都要记；**提示词要点是必填** | [`05-ai-collaboration.md`](../../harness/conventions/05-ai-collaboration.md) §3—§4 |

## 八、附：阶段一的四条经验（**阶段二会再遇到**）

| # | 经验 | 教训 |
|---|---|---|
| 1 | **"没有报错"最危险** | 无 BOM 的 `.sql` 会静默失效 —— 判断成功要看**影响行数**，不能只看没报错 |
| 2 | **强断言必须独立验算** | 阶段一报告里出现过「100% 平账」而证据图显示 `❌` 的情况（ISSUE-010 查出） |
| 3 | **AI 的论证可能悄悄替换概念** | 最有效的检验是追问："**你说的 X 和 Y 是同一个东西吗？**" |
| 4 | **交叉审查最有效** | 阶段一双方各审对方一半，**各自抓到的都是对方"以为自己没问题"的地方** |
