## 三、ISSUE-001 裁决：D1—D5

### D1 · 单库（支持 ISSUE-001）✅

**决策**：取消"仓库 / 操作台"双库位，改为**单库 + 反冲倒扣**（下单即按 `订单明细 × 配方` 扣总库）。

**核心依据 —— week1 反对的不是反冲倒扣**：

week1 §3.4 的原话：
> "这样做的收益：**库存的每一次减少都能追溯到具体订单**。若改成'**领料即出库**'，领了没用完的部分就会变成无据可查的账面差异。"

| | 扣的是什么 | 会不会有"领了没用完"的差异 |
|---|---|---|
| 领料即出库 | 领料量（**估算的**） | ✅ **会** —— 这才是 week1 反对的 |
| **反冲倒扣** | 实际售出量（订单 × 配方） | ❌ **不会** —— 卖多少扣多少 |

**反冲倒扣同时满足 week1 的两个目标**（可追溯到订单 + 无账面差异），且不需要"操作台"这一中间层。

**代价（必须一并接受）**：

1. 推翻 week1 §3.4「小组确认」过的两层库存 → **留痕**；
2. week1 §2.2 第三组职责分离失去载体 → 由 **D6** 处理；
3. D-01 留给第 8 周的重构素材（枚举 → 库位表）作废 → 由 **D8** 处理。

**连带作废的既有决策**：

| 决策 | 命运 |
|---|---|
| **D-01**（库位用枚举域） | ❌ 整条作废 |
| **D-02**（移库写两行） | ❌ 整条作废 |
| **D-03**（只认操作台扣减） | ❌ 整条作废 → 改为**扣总库** |
| D-08a（移库单） | 早已撤销 |

> ⚠️ **顺带损失**：D-01 原本是展示"**SQL Server 无原生 ENUM**"与"**域 vs 实体**"的教具。作废后前者可由糖度/冰量的 `CHECK` 域承担，后者需另找载体。

### D2 · 留报损 ✅（**改判**）

**决策**：保留"打烊报损"，作为库存流水的独立类型。

#### 先记录一次被推翻的论证

> **我最初的反对理由是错的，原话如下：**
> "单库反冲之后，'操作台剩余'这个概念本身就不存在了，报损失去了触发场景。"

**同事（用户）的追问戳中了要害**：

> **数据库意义的"操作台"和实际报损的物理操作台一样吗？**

**答案：不一样。** 这个论证因此作废。

| | 数据库里的"操作台库位" | 现实里的"吧台半成品" |
|---|---|---|
| 是什么 | `location_code='COUNTER'` —— **同一个 `ingredient_id` 的数量分布** | 一锅**煮好的珍珠**、一桶**泡好的茶汤** |
| 物料变了吗 | **没变** —— 干珍珠还是干珍珠 | **变了** —— 珍珠吸水、有 4 小时保质期；茶包变茶汤、茶渣废弃 |
| 靠什么存在 | 靠"领料/移库"这个设计动作 | 靠**物理事实**存在，与数据库怎么建模无关 |

**取消数据库的库位维度，取消不了"吧台上有一批会过期的半成品"这个物理事实。** 两者正交。

#### 改判后的真实依据

**报损与盘盈亏是两类不同的业务事实**：

| | 报损 | 盘盈亏 |
|---|---|---|
| 原因 | **已知** —— 打翻了、超时报废 | **未知** —— 账实不符，查不出来 |
| 责任人 | **有**（当班制作员登记） | 没有 |
| 发生时机 | 随时（打烊称重是典型场景） | 月度盘点 |

week1 §3.5 原话："**不留 → 所有账实不符一律走「盘盈亏」**" ——
**这等于把所有"已知原因的损耗"塞进"未知差异"，丢失追责线索。**

而 week1 §2.2 花了整节论证三组职责分离，核心论据是"**账实不符时无法追责**"。
→ **留报损，比砍掉它更契合 week1 自己的设计哲学。**

#### 定性修正：这是「落实留白」，不是「推翻」

> **⚠️ 本文件初稿把 D2 写成"与 week1 §3.5 直接矛盾"，说重了。复核 week1 原文后修正如下。**

week1 §3.5 在砍掉两条报废规则之后，**自己留了一个明确未决的口子**：

> "**⚠️ 一个尚未决定的小口子**：**打翻、破损**这类物理损耗要不要留一档？
> - 留 → 库存流水多一种类型，**报损登记有人负责**
> - 不留 → 所有账实不符一律走「盘盈亏」
>
> 默认按**不留**处理（进一步简化）。**若后续觉得需要，再补。**"

**D2 选的正是"留"。所以它的主要性质是"落实 week1 自己留白的那个问题"。**

而且 week1 在列举"留"的收益时写的是"**报损登记有人负责**" —— 这恰恰呼应 §2.2 的追责哲学，与 D2 的改判理由同向。

**但确实有连带修订** —— week1 随后那句条件性陈述因此失效：

| | week1 基线 | D2 之后 |
|---|---|---|
| 流水类型 | 3 类 | **4 类**（+ 报损） |
| 台账平衡式 | `期初 + 采购 − 销售 ± 盘盈亏` | `期初 + 采购 − 销售 − **报损** ± 盘盈亏` |
| "只有三种动作改变总数" | ✅ 成立 | ⚠️ **变成四种** |

> **答辩时的正确说法**："week1 说'若后续觉得需要，再补'，**我们判断需要，补上了**"。
> 而不是"我们推翻了小组决定" —— 两者在评委耳中是完全不同的两件事。

#### 记账约定（必须写死）

报损按**干重当量**记账。举例：

```
采购入库：干珍珠 +1000g                       → 1000g
煮制：干 1000g → 熟 2000g（吸水）
        ↓ 煮制【不记账】
卖 10 杯：熟珍珠 600g = 干重 300g              → 销售耗用 −300g
打翻剩下：熟珍珠 1400g = 干重 700g             → 报损    −700g
                                          合计 1000 ✅
```

**两条铁律**：
1. **煮制 / 泡制不产生库存流水**（在制品形态转换不入账）；
2. **所有流水数量一律用干重当量**，原料表单位即此口径。

**折算率不能是隐藏规则** —— 须写进文档或原料的规格字段。

### D3 · 保留"还能做几杯"视图 ✅（不改）

**依据**：

1. **week1 §4.2 #1 本来就定的是"用视图算，不做物理表"**，§4.3 #3 还特意强调这是派生数据的正确姿势。
   ISSUE-001 的表述是"还试图用 **SQL 视图去实时算**'成品还能做几杯'" —— **把"用视图算"本身当成了错误**，属误读；
2. **性能理由不成立**：30 成品 × 约 22 行配方 ≈ **660 行**。所谓"跨表求 MIN 瓶颈"是 660 行上的聚合，毫秒级；
3. **它直接撞在第 4 周作业上**：当周产出含 `view.sql`（"不同的统计视图"），且评分要看统计视图。
   该视图跨三张表（成品 / 配方 / 原料），是 JOIN + 分组聚合的天然素材，也是答辩能讲出彩的地方；
4. **业务上仍有人看**：给**店长**看，用于补货与提前备料决策 —— 正好接上第 4 阶段"预测驱动补货"。

**职责边界（须写死）**：视图**只算理论上限**，**不掺 `is_sold_out`**。
原因：一旦掺入运营状态，它就无法回答"如果现在把珍珠煮上，能做几杯"，而那恰恰是补货决策要看的东西。

### D4 · 手工沽清 ✅（用 ISSUE-001 的方法）

**决策**：`tbl_ingredient.is_sold_out BIT NOT NULL DEFAULT 0`（**原料级，一个字段，不建表**）。

**核心依据 —— 沽清 ≠ 库存校验**：

| 机制 | 表达的业务语义 |
|---|---|
| **库存校验** | 料**没了**（台账上真不够了） |
| **手工沽清** | 料**有，但现在做不了** —— 冷库有干珍珠，但吧台没煮好的，现煮要 20 分钟 |

**现实场景**：店员看到煮好的珍珠见底 → 点"珍珠沽清" → 前端立刻把所有含珍珠的饮品标售罄 → 新一锅煮好后点回来。

**所以沽清不是库存机制，是运营状态标记**，与库存校验**互补，不能互相替代**。

**形式选择**：

| 形式 | 评价 |
|---|---|
| **`tbl_ingredient.is_sold_out`** ⭐ | **采用** —— 点一次"珍珠沽清"，含珍珠的饮品自动售罄 |
| `tbl_product.is_sold_out` | 成品级更直接，但点一次要手工标 5 款饮品 |
| 独立 `tbl_soldout` 表 | 能记时间/原因/操作人，但 week1 边界里无此对象，第一阶段过重 |

**额外收益**：`原料 → 配方 → 成品` 的售罄推导，又是一个第 4 周的视图素材。

**⚠️ 对 week1 的补充**：数据边界新增"**沽清状态**"对象（week1 §4.1 的 19 项进库清单里没有它）→ 留痕。

### 🟡 与 week1 基线的连带修订：D2

已在 D2 中详述。**定性是「落实 §3.5 的留白 + 连带修订」，不是推翻** ——

### 须写死的 4 处接口

| # | 接口 | 约定 |
|---|---|---|
| **1** | **D2 × D1** | 报损一律按**干重当量**记账；煮制/泡制不产生流水。否则单位混用，台账立刻崩 |
| **2** | **D2 × D4** | 报损后系统仍会认为"可做"（干料还够），但吧台实际无熟料 → **须同时点"沽清"**。两件事在数据库里正交，操作上要配套 |
| **3** | **D3 × D4** | 视图**只算理论上限**，不掺 `is_sold_out`；前端的"售罄"由另一查询做 `库存不足 OR 沽清` |
| **4** | **D4 × D1** | `is_sold_out` 落在 `tbl_ingredient` 上 —— **正因为 D1/D7 把字典与台账合成一张，这个字段才有无争议的落点** ✅ |

### 互相加强的 4 处

| 组合 | 效果 |
|---|---|
| **D1 × D3** | 单库后视图**更简单** —— 不用按库位过滤 |
| **D1 × D4** | 单库解决"没料了"，沽清解决"有料做不了" —— **互补，缺一不可** |
| **D2 × D5** | 留报损让 v0.1 有了"已知损耗"出口，**缓解了 D5 延后盘点的张力** |
| **D5 × D3** | 两者都是"理论值"口径，**更自洽** —— 若盘点会调整库存，视图数字会突变，反而更令人困惑 |

### 额外收益：D4 部分补回了 D1 删掉的东西

D1 删掉移库后，第三组职责分离失去载体。
而"**谁来点沽清**"给了它一个新落点 —— **沽清是物料状态，归制作员**；库管员管的是**库存数量**。

### 一处 week1 连带失效

week1 §3.6 写的是"**按库位分别盘**：仓库、操作台各盘一次" —— D1 取消库位后这句失效。
→ **盘点明细不再需要 `location_code`**。虽盘点已延后（D5），但此条须写进修正汇总，否则第 2 阶段补建时会照抄 week1 的旧描述。

## 五、D6—D8

### D6 · 第三组职责分离的替代表达 ✅

**问题**：删掉移库后，"制作员往外拿 / 库管员往里收+数账"没了载体；而制作员要登记**报损**、库管员要登记**采购入库**，两人都对库存流水有写权限。

**解法：分离点不在流水表，在 `tbl_ingredient`。**

| 角色 | `tbl_ingredient` | `tbl_stock_ledger` | 采购单 |
|---|---|---|---|
| **制作员** | **只读** | INSERT + SELECT（登记报损/耗用） | 只读 |
| **库管员** | **可写 UPDATE**（调整库存量、设补货点） | INSERT + SELECT（登记采购入库） | 只读 |
| **收银员** | 只读 | 只读 | ✘ |

### ⚙️ 连带补丁（漏洞 1 采纳后必须同步修改的两处既有决策）

`tbl_spec_option` 建表后，**D-07 与 D-05a 都要改**：

```
tbl_spec_option
  spec_option_id  INT IDENTITY   PK
  spec_type       VARCHAR(10)    CHECK IN ('CUP','SUGAR','ICE')
  spec_code       VARCHAR(6)     'M'/'L' | 'NONE'/'S30'/'S50'/'S70'/'FULL' | 'NO_ICE'/'LESS'/'NORMAL'/'HOT'
  spec_name       NVARCHAR(10)   '中杯'/'大杯' | '无糖'/'三分糖' …
  extra_price     DECIMAL(10,2)  NOT NULL DEFAULT 0     -- ★ 大杯 +3.00 的落点
  sort_no         INT            NOT NULL
  ── UNIQUE (spec_type, spec_code)                       ← 候选码
```

| 补丁 | 原设计 | 改为 |
|---|---|---|
| **D-07** | `tbl_order_detail` 的 `cup_size` / `sugar_level` / `ice_level` 三个 `VARCHAR + CHECK` 列 | **改为三个外键** `cup_spec_id` / `sugar_spec_id` / `ice_spec_id` → `tbl_spec_option` |
| **D-05a** | `tbl_recipe` 的 `sugar_level = 'ANY'` **哨兵值** | 改为 `sugar_spec_id` **允许 NULL** 表示"与糖度无关" |

**D-05a 为什么可以用 NULL 顶掉哨兵**：SQL Server 的 `UNIQUE` 约束**把 NULL 视为相等**，所以
`UNIQUE (product_id, cup_spec_id, sugar_spec_id, ingredient_id)` 在 `sugar_spec_id` 为 NULL 时**只允许存一行** —— 唯一性照样成立，"与糖度无关"这件事仍被约束保证。

**附带收益**：订单明细一下子多出**三个可标注的真外键**，正对作业"标注外码"的要求。

> **顺带修正一处认知损失**：D-01（库位枚举）作废后我曾担心"**域 vs 实体**"这个教学点没了。
> 现在它被补回来了，而且**同一份设计里两种处理并存**，对照反而更清楚：
> 岗位 / 流水类型等**无自有属性** → `CHECK` 域；规格选项**有自有属性**（加价、排序、显示名）→ **物化为表**。
