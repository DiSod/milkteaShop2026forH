### 3.3 ⭐ 一条 AI 论证被追问后推翻（第 2 周）

> 这是**最典型的一条**：AI 的论证表面自洽，但**混淆了两个不同的概念**。

| | |
|---|---|
| **AI 的论证** | "单库反冲之后，'操作台剩余'这个概念本身就不存在了，**报损失去了触发场景**" —— 据此建议砍掉报损 |
| **错在哪** | 它把**数据库意义的"库位"**与**现实中的"在制品"**当成了同一个东西。<br>· 数据库的"操作台库位"只是**同一物料的数量分布**（可合并）<br>· 现实的"吧台半成品"是**形态已变的在制品**（珍珠吸水、茶汤泡出）<br>**两者正交** —— 单库反冲不影响现实中的损耗 |
| **怎么发现的** | 人工一句追问：**"数据库意义的操作台和实际报损的物理操作台一样吗？"** |
| **怎么改的** | **该论证作废，D2 改判为「留报损」**；17 表里的 `LOSS` 流水类型由此保留 |
| **教训** | AI 的论证**读起来很顺，但它可能悄悄替换了概念**。<br>**追问"你说的 X 和 Y 是同一个东西吗"是最有效的检验。** |
| **证据** | [`week02/schema-design.md`](../../week02/schema-design.md) 第九节；完整推翻过程在 [`issue-review.md`](../../week02/issue-review.md) 的 D2 一节 |

### 3.7 ⭐ 无券退单积分约束死锁（第 3 周）

| | |
|---|---|
| **AI 生成的约束** | `ck_points_ledger_target` 要求 `point_type = 'REDEEM'` 时 **`coupon_id` 必须非空** |
| **错在哪** | 它只想到了"积分兑券"，**忘了"退单积分回滚"也是 REDEEM** —— 而**超过 90% 的自费订单没有用券**。<br>→ 这些订单一旦退单，插入扣回积分流水会**直接触发 CHECK**，**全店无券订单退单 100% 崩溃** |
| **怎么发现的** | **工程侧实测复现**：`INSERT … VALUES (1,'REDEEM',-5,1,NULL)` → **`Msg 547`** |
| **怎么改的** | 放宽为 `coupon_id IS NOT NULL **OR** order_id IS NOT NULL` |
| **教训** | **AI 的约束往往只覆盖"主用例"，漏掉边界**。<br>**用负例测试去撞它** —— 这一条正是被"故意插非法数据"的测试思路反向发现的 |

### 3.8 ⭐ 退单库存回冲：多对一 UPDATE 吞行（第 3 周）

| | |
|---|---|
| **AI 生成的语句** | `UPDATE i SET i.qty_on_hand = i.qty_on_hand + l.qty FROM tbl_ingredient i JOIN tbl_stock_ledger l ON l.ingredient_id = i.ingredient_id WHERE l.remark = N'订单取消回冲'` |
| **错在哪** | 当同一原料**有多次回冲**时，`UPDATE … FROM … JOIN` 会**随机挑其中一行**叠加，**其余被静默吞掉** —— 这是 SQL Server 的经典陷阱 |
| **怎么发现的** | **实测**：初始 100g，发生 +10g 与 +20g 两次回冲，**预期 130g，实得 110g**（丢了 20g） |
| **怎么改的** | 改为按订单分组的聚合子查询：`JOIN (SELECT ingredient_id, SUM(qty) … GROUP BY ingredient_id) r` |
| **教训** | **`UPDATE … FROM … JOIN` 在"多对一"时不保证确定性** ——<br>AI 爱用这种写法因为它简洁，**但一遇到"多条匹配"就出错，而且不报错** |
| **证据** | [`harness/issues/008`](../../../harness/issues/008-points-refund-and-crud-robustness.md) 证据 ② |

### 3.9 采购加权成本除零击穿 NOT NULL（第 3 周）

| | |
|---|---|
| **AI 生成的公式** | `moving_avg_cost = (qty_on_hand*old_cost + qty_received*price) / NULLIF(qty_on_hand + qty_received, 0)` |
| **错在哪** | `NULLIF(…, 0)` 在**分母为 0 时返回 `NULL`** —— 而 `moving_avg_cost` 是 `NOT NULL` → **Error 515** |
| **怎么发现的** | **实测**：模拟"初始库存 0 + 到货因变质全部拒收（实收 0）" |
| **怎么改的** | 改 `CASE WHEN (qty_on_hand + qty_received) > 0 THEN … ELSE i.moving_avg_cost END` |
| **教训** | **`NULLIF` 防除零只是"把错换成另一种错"** ——<br>它给的是 `NULL`，而目标列不接受 `NULL`。**必须先想清楚分母为 0 时业务上应该是什么** |
| **证据** | [`harness/issues/008`](../../../harness/issues/008-points-refund-and-crud-robustness.md) 证据 ③ |

### 3.10 建库脚本"静默失效"—— 编码问题（第 3 周）

> ⚠️ **性质说明**：这条**不是 AI 的判断错误**，而是"AI 起草的脚本在我们环境里跑不通"。
> 一并收录，因为它同样体现"**必须实测**"。

| | |
|---|---|
| **现象** | AI 起草的 `create-database.sql` **首次执行看起来成功，实则一行都没生效** —— 且**没有任何报错** |
| **错在哪** | **文件编码**：`.sql` 存为无 BOM 的 UTF-8，`sqlcmd` 按系统 GBK 读取 → 中文被解错 → **整个批次静默失效** |
| **怎么发现的** | **对照实验**：同一条 `INSERT`，无 BOM 时 **`(0 行受影响)`**，补 BOM 后 **`(3 行受影响)`** |
| **怎么改的** | 全部 `.sql` 存为 **UTF-8 with BOM**；执行时**再加 `-f 65001` 双保险**；写进规范 §9 |
| **教训** | ⭐ **"没有报错"最危险** —— 它会让 1.9 MB 的种子数据看起来装载成功，实际一行都没进去。<br>**判断脚本成功与否要看"影响行数"，不能只看"没报错"** |
| **证据** | [`harness/conventions/02-sql-style.md`](../../../harness/conventions/02-sql-style.md) §9 |

### 3.11 `collation_name = NULL` 被误判为缺陷（第 3 周）

> ⚠️ **性质说明**：这条是**我们自己（AI 辅助下）的误判**，不是 AI 的错。收录因为教训等价。

| | |
|---|---|
| **AI 的判断** | 库刚建好时查 `sys.databases.collation_name` 返回 `NULL` → 报告"**排序规则没设上**" |
| **错在哪** | 这是 **SQL Server 元数据的惰性填充** —— 数据库在**首次被打开前**，该列就是 `NULL` |
| **怎么发现的** | **对照实验**：先 `USE milktea_shop`，再查即返回 `Chinese_PRC_CI_AS` |
| **怎么改的** | 确认**非 bug**；在脚本里补 `USE` 触发元数据打开 |
| **教训** | **`NULL` 不等于"没设置"** —— 系统视图的惰性行为要用**对照实验**排除，不能直接下结论 |
| **证据** | [`weeks/week03/README.md`](../../week03/README.md) 问题表第 3 条 |

### 3.12 `$W` 与 `$w` 是同一个变量（第 4 周）

| | |
|---|---|
| **AI 生成的代码** | 图像宽度存在 `$W` 里，网格线循环又写 `foreach ($w in $colW)` |

| **教训** | 在大小写不敏感的语言里，**单字母变量名是雷区**。<br>这是本会话第三次踩同类坑（`$pid`、`$home` 也曾被误用） |
| **证据** | [`result/render.ps1`](result/render.ps1) 的注释 |

### 3.13 自定义函数 `R` 撞上内置别名（第 4 周）

| | |
|---|---|

## 4. 被否决 / 反转的 AI 方案

> **被否决的方案不是失败，是证据** —— 它们证明小组**逐条评估过**，而不是照单全收。

### 4.1 经营场景选"小卖部" → **否决**

| | |
|---|---|
| **AI 的建议** | 经营场景选小卖部（理由是"数据好找、结构简单"） |
| **否决理由** | **结构过于单薄** —— 小卖部只有整进整出，没有"配方(BOM)"这一层，商品与库存是 1:1，撑不起课程的建模深度 |
| **替代方案** | **奶茶店（单店）** —— 商品 ↔ 库存之间隔着配方，天然多一个层次；订单有"点单→制作→取餐"状态流转 |
| **判断依据** | 课程要求的 6 实体覆盖度 + 结构完备性 |

### 4.2 "报损失去了触发场景" → **推翻**

| | |
|---|---|
| **AI 的建议** | 单库反冲后没有"操作台"，报损无触发场景 → 建议砍掉 `LOSS` 流水类型 |
| **否决理由** | **混淆了两个概念** —— 数据库"库位"是同一物料的数量分布；现实的"吧台半成品"是**形态已变的在制品**。**两者正交** |
| **替代方案** | **保留报损**（D2 改判）；17 表中 `LOSS` 类型保留 |
| **判断依据** | 人工追问后的复核结论（见 §3.3） |

### 4.3 22 张表的表清单 → **撤销一张 + 砍 3 个字段**

### 总结

本阶段 AI 承担的是**草稿与候选方案的产出**，小组承担的是**判断、修改与验证**：

| 维度 | 事实 |
|---|---|
| 使用规模 | **10 条**实质记录（第 1—4 周） |
| **人工把关的直接证据** | **§3 的 13 条出错案例** + **§4 的 7 条被否决方案** |

> **留痕的价值不在于证明"用了 AI"，而在于证明"人把关了"。**

> 而是 §3 里那些**被追问、被实测、被推翻**的地方 ——
> 尤其 §3.3（一句追问推翻一条论证）、§3.7—3.9（实测撞出三个 SQL 边界缺陷），
