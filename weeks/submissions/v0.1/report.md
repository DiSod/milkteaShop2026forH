# 1. 设计思路

## 1.1 业务背景与范围

**经营场景**：校园 / 商圈临街**单店**茶饮店「茶颜小铺」，营业 10:00—22:00，全年无休。

| 项 | 设定 | 来源 |
|---|---|---|
| 门店数量 | **1 家**（单店，不做连锁） | 课程要求 |
| 菜单规模 | 约 **30 款**成品 | week1 §1.1 |
| 原料规模 | 约 **60 种**（茶叶、奶基底、糖浆、小料、包材） | week1 §1.1 |
| 营业模式 | 堂食 + 自提，**不接**外卖平台 | week1 §4.4 |
| 日均订单 | 200—400 单；客单价 12—20 元 | week1 §1.1 |

**核心对象**：课程要求覆盖 6 类 —— 商品、库存、订单、订单明细、会员、员工。全部覆盖。

**本场景的结构特征（选它的理由）**：

```
小卖部：  商品 ──1:1── 库存              （卖一包薯片，库存减 1）

奶茶店：  商品 ──配方(BOM)── 原料库存      （卖一杯珍珠奶茶 = 珍珠 −20g + 红茶 −5g + …）
```

**商品与库存之间隔着"配方"这一层** —— 这是奶茶店区别于小卖部的根本，也是本项目所有设计难点的来源。

## 1.2 设计目标

**课程阶段目标**：把一个真实经营场景转化为**可运行的关系数据库**，完成最小但完整的数据闭环 ——
建库、装载、增删改查、连接查询、视图、完整性与授权。

**本次设计的四个自设目标**：

| # | 目标 | 衡量方式 |
|---|---|---|
| 1 | **结构一次到位** | 17 张表覆盖全部业务对象，不留半成品 |
| 2 | **完整性由数据库强制** | 关键约束全部落到 DDL，而非应用层自觉 |
| 3 | **可追溯到业务依据** | 每一次库存变动都能追溯到具体单据 |
| 4 | **为后续阶段留出演进空间** | 有意的延后项 = 第 2 阶段模式重构的素材 |

## 1.3 关键设计决策与取舍 ⭐ **（答辩重点）**

> 本节是评分"能否解释清楚设计思路"的直接落点。
> 完整记录见 [`weeks/week02/schema-design.md`](../../week02/schema-design.md)（设计决策 D-01～D-12）
> 与 [`weeks/week02/issue-review.md`](../../week02/issue-review.md)（裁决 D1—D8）。

### 1.3.1 由小组拍板的三个基本决策

| 决策 | 结论 | 理由 |
|---|---|---|
| **经营场景** | **奶茶店（单店）** | **结构完备优先于数据现成**：公开数据中不存在单店奶茶的库存/进货记录，我们宁愿自建数据，也要拿到"配方"这一层 |
| **数据策略** | **母本 + 自建** | 公开数据只承担两个角色：销量分布的**母本**、结构设计的**范本** |
| **复杂度控制** | 原料 ≤ 60 种、菜单 ≤ 30 款、不接外卖、不做多门店、配方不做版本 | 对应课程"不要太复杂"的要求 |

### 1.3.2 库存模型：从"两层移库"改为"单库反冲"（**重要取舍**）

| | 原方案（week1 §3.4，小组确认过） | **改后（D1）** |
|---|---|---|
| 库存维度 | 仓库 + 操作台**双库位**，主码 `(原料, 库位)` | **单库**，只要原料 |
| 领料 | **移库**：写两行流水（出 / 入） | **无领料动作** |
| 扣减 | 销售耗用扣**操作台** | **下单即按 `订单明细 × 配方` 反冲扣总库** |
| 流水类型 | 6 类 | **3 类**（采购入库 / 销售耗用 / 报损） |

**改的原因**：week1 反对的是"**领料即出库**"（领料量是估算的，会产生无据可查的账面差异）；
而**反冲倒扣扣的是实际售出量**，同样能追溯到订单，却不产生该差异，还省掉整个中间层。

**代价（如实记录）**：week1 §2.2 的**第三组职责分离**（制作员 vs 库管员）失去结构载体 →
改为在**表级权限**上表达：制作员对 `tbl_ingredient` **只读**、库管员**可写**。

### 1.3.3 三组"刻意不重叠"的职责分离（权限设计的依据）

| # | 分离 | 落点 | 目的 |
|---|---|---|---|
| 1 | **收银员 vs 店长** | 收银员**不能改价**，改价权归店长 | 价格改动必须留痕 |
| 2 | **收银员 vs 制作员** | 一人碰**金额线**，一人碰**物料线** | 便于事后追责 |
| 3 | **制作员 vs 库管员** | 制作员**只读**库存、库管员**可写** | 一人既管收又管发则无法追责 |

### 1.3.4 被否决的方案（**答辩时能讲出"考虑过并主动放弃"**）

| # | 方案 | 否决理由 |
|---|---|---|
| 1 | **小卖部场景** | 结构只有"整进整出"，没有配方这一层；改为奶茶店 |
| 2 | **供应商实体** | week1 曾三选一选了"完全不记"；**裁决时被推翻**（见 1.3.5），改为补建 4 字段极简表 |
| 3 | **库位独立建表** | 库位只有两个固定值且不带属性 → 用 `CHECK` 域即可；**该决策随后随 D1 整体作废** |
| 4 | **支付记录独立建表（一对多）** | 「支付失败重试」是**流程分支**，不是数据需求；改并入订单头 |
| 5 | **优惠券拆模板 + 实例** | 第一阶段只有"5 元券"一种形态，**不存在"模板"概念**；合并为一张，拆分留作第 2 阶段规范化素材 |
| 6 | **损耗报损不做** | week1 曾砍掉；裁决时**留白被落实** —— 改为**保留报损**（原因已知、有责任人，与"未知差异"性质不同） |
| 7 | **排班与交接班** | 业务活动真实存在，但**记录不进库** —— 这是"数据边界"的典型案例 |
| 8 | **原料批次追溯** | 复杂度高；注明"第 2/3 阶段视进度再议" |
| 9 | **供应商联系人 / 账期 / 银行账户** | 边界保持 —— 只记 4 个字段用于外键标识 |

### 1.4.2 表的分类

### 1.4.3 核心结构：配方的两层展开

**扣料不是一路，是两路** —— 这是本项目最重要的结构结论：

```
应耗用 = Σ (固定配方.qty × 明细数量)          ← tbl_recipe
       + Σ (小料.qty_per_serving × 加料份数)   ← tbl_topping
```

**为什么必须分开**：固定配方描述"这款成品**固定**用哪些料"；而"加珍珠"是顾客在**订单上可选**的增量。
同一杯珍珠奶茶，有人加椰果有人不加 —— 所以加料用量**不能进配方表**。

**一个具体验证**（取自样例数据）：

```
订单 1 的珍珠奶茶是大杯 → 配方 28 g
              + 加珍珠一份 → qty_per_serving 20 g
              = 库存流水实记 48 g      ✅ 对得上
```

### 1.4.4 完整性约束的三个抓手

| # | 抓手 | 落点 |
|---|---|---|
| 1 | **库存非负** | `CHECK (qty_on_hand >= 0)` —— 把"库存必须真实"变成**结构上不允许为负** |
| 2 | **积分非负** | `CHECK (points_balance >= 0)` |
| 3 | **零弱类型外键** | 库存流水的"来源"用**判别列 + 3 个真外键**，而非一个字符串 `ref_no` |

### 1.4.5 有意的延后（= 第 2 阶段重构素材）

| # | 素材 | 重构内容 |
|---|---|---|
| 1 | 优惠券 1 张 → 2 张 | 拆分，消除"模板属性对实例的部分依赖" |
| 2 | 支付并入订单头 → 拆出 | 一对多建模 |
| 3 | 盘点 0 → 2 张 | 补建单据与明细 + 加外键 |
| 4 | 价格历史 0 → 1 张 | 引入审计表 |
| 5 | 流水类型 3 类 → 4 类 | `ALTER` + 约束迁移 |

### 2.3.1 三个"写表清单才暴露"的设计漏洞

| # | 漏洞 | 结论 |
|---|---|---|
| 1 | **大杯加价放哪** —— week1 的商品表只有一个"售价" | 裁定"**全店统一加价**" → 加价是**杯型的属性** → 建 `tbl_spec_option`（它携带加价/排序/显示名） |
| 2 | **补货点 / 目标水位放哪** —— week1 写在"原料库存"的括注里，但库存表主码是 `(原料, 库位)`，两行会重复存同一值 | 移到 `tbl_ingredient`（它们是**原料的采购策略参数**，不是库位的属性） |
| 3 | **原料"保质期"字段** —— §4.1 #5 列了，§3.5 却说"暂定原料不会过期" | **删除** —— §3.5 已砍过期管理，该字段是**裁剪时漏删的残留**；且 §4.4 已给批次追溯留了"第 2/3 阶段再议"的后路 |

> **方法论收获**：三个漏洞**全部**是在"写表清单/填字段"这一步暴露的，不是在讨论决策时想出来的。
> **"先把表名和字段名写出来"是有效的自检手段** —— 它比反复推敲单条决策更能发现问题。

### 2.3.2 一次 AI 参与但被人工纠正的记录

| 项 | 内容 |
|---|---|
| AI 的论证 | "单库反冲之后，'操作台剩余'这个概念本身就不存在了，报损失去了触发场景" |
| 人工质疑 | "**数据库意义的操作台和实际报损的物理操作台一样吗？**" |
| 复核结论 | **不一样** —— 数据库的"操作台库位"只是同一物料的数量分布；现实的"吧台半成品"是**形态已变的在制品**（珍珠吸水、茶汤泡出）。**两者正交** |
| 处理 | 该论证作废，D2 **改判为留报损**，并把这次推翻过程**写进了裁决意见**（`05-ai-collaboration.md`：AI 出错并被纠正的案例最有价值） |
