## 二、分工模式

本组**不按"一人写代码、一人写文档"切分**，而按「**谁对哪一块负责最清楚**」切分，
并且**每一方都要审查对方的产出**：

| | 设计侧（胡博锐） | 工程侧（何争霖） |
|---|---|---|
| **主责** | 业务需求 → 关系模式 → 数据字典 → 阶段报告 | 造数引擎 → 第 4 周 SQL → Issue 看板机制 |
| **SQL 分工** | **第 3 周全部**（建库 / 建表 / 约束 / 索引 / CRUD） | **第 4 周全部**（查询 / 视图 / 安全） |
| **交叉审查** | 复核第 4 周交付，验算强断言，**修掉 5 处与事实不符** | 审查第 3 周脚本，**实测挑出 3 个边界缺陷** |

> **这个安排的好处**：**第 3 周我写 SQL，第 4 周他写 SQL**，各占一半；
> 同时**每一方都在审对方那一半** —— 所以代码量天然接近 50/50，且双方都完整经历了"设计与实现"。

### 边界约定

依据 [`harness/team/README.md`](../../../harness/team/README.md) 与
[`04-git-workflow.md`](../../../harness/conventions/04-git-workflow.md) §2.1：

| 内容 | 归谁 |
|---|---|
| `project/docs/**`、`weeks/**`、`harness/conventions/**`（文档） | **文档主编**执笔 |
| `project/sql/**`、`project/data/**`（代码与数据） | **核心工程**主责；第 3 周 SQL 由文档主编承担 |
| `harness/issues/**`（看板） | 双方均可提报；**由对方裁决** |

### 占比

| 成员 | 第 1—4 周 | 占比 |
|---|---|---|
| **胡博锐** | 设计 / 文档 / 第 3 周 SQL / 复核 | **55 %** |
| **何争霖** | 造数引擎 / 第 4 周 SQL / 代码审查 / 看板机制 | **45 %** |
| | | **100 %** |

**为什么不是按行数的 75 : 25**

> 行数会**系统性低估工程侧**的价值：
> - 他的 `generate_seed.py`（1,479 行）**产出了 20,979 行种子数据**，杠杆远大于行数比；
> - 他实测挑出的 **3 个边界缺陷**（积分约束死锁 / 多对一吞行 / 除零）**每一个都会在生产环境造成真实损失**，
>   而这类贡献**一行代码都不占**；
> - 他建立的 **Issue 看板与协作规范**是全项目的机制基础。
>
> 综合判断为 **55 : 45**。
