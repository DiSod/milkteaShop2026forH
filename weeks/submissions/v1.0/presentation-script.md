### 2.2 三层怎么在演示里串起来

六层是"技术上发生了什么"，三层是"代码该写在哪"。演示时**不要另外花一页讲架构**，把三层挂到三个动作上就行：

| 动作 | 你做的操作 | 嘴里说的那一句（点明层） |
|---|---|---|
| **① 一次合法写入** | 库管台报损 1.5g → 提交 | "这个表单只提交两个字段，**路由层只取参数不做判断**；数量、超结存、缺原因这些错都是 **service 抛的**；真正写库的是 **dao 里那条带 `?` 的 SQL**。" |
| **② 一次被拒** | 同一页,报损 99999999g | "它没写进库——**service 算出会变负库存，直接 409**，数据库根本没被碰。"（指 409 页面） |
| **③ 一次越权** | 库管访问 `/manager` | "**页面层跳转 → service 校验 → 数据库 GRANT**，三层各拦一次；这次是数据库先不让他读（229），service 把它翻成 403。"（指 403 + 229 两张图） |

**串起来的那句话**（在第 6 页说完、切到第 7 页之前说）：

> 这三层不是三个文件夹，是三条不能越界的线：页面不许写 SQL，service 不许碰连接，只有 dao 能拼 SQL。越界会被 `tests/test_layering.py` 抓到——它现在是我们 46 条测试里最便宜的三条。

**一个业务两处入口**（有余量时补，收银台那页说）：`会员自己点单` 和 `收银员代客下单` 走的是**同一个 `ordering.place_order()`**，差别只在传不传会员号——这就是"业务逻辑只在 service 有一份"的直观证据。

### 3.4 第 4 页 · 规范化【可跳】

> 规范化我们只动了该动的地方：**15 张纯净 BCNF**，3 张留了受控冗余。
> 这三列是会员积分余额、订单应收、明细小计——留着是为了少一次聚合，代价是必须**只有一个写入口**。
> 有一点值得说：商品编号能决定**当前**名称，但决定不了**历史成交价**。

**跳页时**：直接说"规范化这块我们放在报告里，这里跳过"，切第 5 页。

---

**这一页怎么讲（BCNF 到底怎么体现）**：不要背定义，按五步走。

1. **一句话定义**：`每个非平凡函数依赖的决定因素都是超码`——翻译成人话：表里每一列被别的列决定时，"决定它的那几列"必须能唯一确定一整行。
2. **我们怎么判的**：先把 18 个唯一约束当候选码列出来（`uq_*` 一共 18 条，覆盖 17 张表；两张纯流水表按设计没有业务候选码），再逐表查三件事——有没有"半个码决定非主属性"（2NF）、有没有"非主属性决定非主属性"（3NF 传递）、有没有"决定因素不是超码"（BCNF）。
3. **一个真反例，修好了**：券表原来是 11 列，面额和门槛是**活动属性**，跟券号无关；同一个活动的 12 张券各存一份面额。也就是说"模板 → 面额"，而**模板不是券的超码**——BCNF 不满足。第 6 周把它拆成 `tbl_coupon_template`（2 行）与 `tbl_coupon`（8 列、24 张），面额只存一份。
   顺带答一句"拆了还能拼回来吗"：实例 ⋈ 模板（按 `template_id`）就是原表，**无损连接**；"模板决定面额"这条依赖仍然在模板表里成立，**依赖保持**。证明在 `normalization.md` §5.3。
4. **一个故意不拆的**：`tbl_order_detail.subtotal = qty × unit_price + Σ加料`。它由整码（`order_id, line_no`）决定，又不决定别的属性 → 单表看满足 BCNF；但它和"明细合计"重复存了一份，属于**有意的受控冗余**，靠唯一写入口 + 每次回归复算（TC-10/TC-11）保证一致。`tbl_member.points_balance`、`tbl_order_header.amount_due` 同理。
5. **收口**：`所以我们的结论不是"全都 BCNF"，而是"15 张干净，3 张明知故犯但控住了，需要拆的 0 张"`。

**如果老师追问"怎么证明不是拍脑袋"**：`project/docs/normalization.md` §3 有一张 18 行的判定表（每表一行的候选码、主要 FD、判定结论），§5 有三组无损连接与依赖保持的证明。

### 3.5 第 5 页 · 七段迁移：每段"从什么变成什么"

> 结构变更只有一条通道 `11-migration/`，**七段，顺序固定，每段自己带回滚**。
> 我不念 CHECK 的名字，只说每段把什么变成了什么：
> 1. 券：原来 11 列里混着面额、门槛，同一个活动的 12 张券各存一份 → **拆成模板 2 行 + 实例 24 张**，面额只存一份。
> 2. 登录：原来只有手机号，知道号码就等于能进 → **加 `password_hash`**，盐用主键，85 条凭据全部有摘要。
> 3. 积分：余额是直接写进去的，流水只记消费送分 → **加 `OPENING` 类型回填 80 条期初**，让"余额 = 流水"成立，25,224。
> 4. 时间：只有下单时间，付款可以早于下单 → **两条 CHECK**（付款 ≥ 下单、完成 ≥ 付款）；但也留了 37 张历史反例，所以没加"付款状态非空就必须有付款时间"。
> 5. 精度：单价是两位小数，加料累加后差几分钱 → **6 个单价列升到四位**，视图重算。
> 6. 取消：状态只能往前，没有"取消"这件事 → **加两类流水**（库存回冲、扣回积分），改两条 CHECK。
> 7. 券核销：一张券能挂两张单、`USED` 和核销时间能互相矛盾 → **一致性 CHECK + 过滤唯一索引**，再默认发 6 张可用券。
> 七段跑完：18 表 / 139 字段 / 49 CHECK / 21,067 行，一段不对就整段回滚。

**手指动作**：手沿时间轴从左划到右，**每个节点只说一句"从…变成…"**，别停下来解释 CHECK。如果感觉偏慢，只讲第 1、3、7 段（券、积分、核销），其余一句带过。

**为什么必须走 migration 而不是改建表脚本**：v0.1 的建表脚本已经冻结、`99-rebuild` 要能一键复原；新建表能重跑，改已有数据不能重跑。

## 5. 可能被问到的问题

### 5.1 如果被问"这 18 张表都是干什么的"

**先说一句总结，再按组念**（不要一张一张念，会冷场）：

> 18 张表里只有 3 张是真业务单据（订单头、订单明细、明细加料），其余都是它们要指的主数据，外加两张只增不改的流水表——积分流水和库存流水。

然后按七组过一遍（每组一句）：

| 组 | 表 | 一句话 |
|---|---|---|
| 点单交易（3） | `tbl_order_header` / `tbl_order_detail` / `tbl_order_detail_topping` | 一张订单头 + 若干明细行 + 每行的加料；金额在头，单价与数量在明细 |
| 商品与配方（4） | `tbl_product` / `tbl_product_category` / `tbl_spec_option` / `tbl_recipe` | 卖什么、有什么可选规格、每款用多少原料（配方表同时承担"这个商品有哪些杯型/糖度"） |
| 加料（1） | `tbl_topping` | 珍珠、椰果这类可加项，单价单独一张表 |
| 会员与券（3） | `tbl_member` / `tbl_coupon` / `tbl_coupon_template` | 谁在下单、他手上有什么券、券的面额与门槛存在模板里 |
| 积分（1） | `tbl_points_ledger` | 每一笔积分变动（含期初 `OPENING`），余额由它加出来 |
| 库存与采购（4） | `tbl_ingredient` / `tbl_stock_ledger` / `tbl_purchase_order` / `tbl_purchase_order_detail` | 原料结存、出入库流水、采购单与明细 |
| 供应与人员（2） | `tbl_supplier` / `tbl_employee` | 供应商；员工（岗位决定数据库角色） |

**若问"为什么是 18 不是 17"**：第 18 张是 `tbl_coupon_template`。把面额/门槛从券实例里提出来，才能同时做到"一券一单"和"面额只存一份"。

**若问"两张流水表为什么没有主码以外的唯一约束"**：流水只追加、不更新，业务上不需要候选码；它们的价值在"每一行都能对上一条业务动作"，这一点由 `order_id` / `ref_type` 和 `CHECK` 保证。

---

| 问题 | 答法 |
|---|---|
| 为什么不用 ORM？ | 课程要看 SQL 能力，也要参数化查询。三层里只有 dao 写 SQL，参数化集中在一处，拼接 SQL 一处都没有。 |
| **怎么证明是参数化，不是拼接？** | 现场做：登录框输入 `' OR 1=1 --`，页面回「手机号或密码不正确」，**不报 SQL 错误、也不会登进去**。里面是 `?` 占位符，值是单独交驱动的。 |
| 18 张表还能再拆吗？ | 15 张已经是纯净 BCNF，剩下 3 张是刻意的冗余列，拆了要多一次聚合；它们都有唯一写入口保证一致。 |
| 券为什么要拆两级？ | 面额、门槛是"这类券"的属性，跟具体券号无关；不拆就要在 12 张券上重复存同样的面额，改一次要改 12 行。 |
| 会员为什么看不到积分流水？ | 数据库角色没有那张表的读权限；放开就等于让收银员能读全部会员的流水。界面给了提示，没有假装有数据。 |
| 两个人同时下单会超卖吗？ | 会——查库存和扣库存之间有窗口。v2.0 按原料 ID 排序加锁，并写并发脚本先复现再证明解决。 |
| 迁移脚本能重复跑吗？ | 不保证，课程也不要求；README 写了运行前提和失败恢复（从 00 重跑）。 |
| 数据是真的吗？ | 种子生成器按业务规则造了 1,963 单、2,629 条明细，约束全部通过；每张证据图都有可重跑的命令。 |
| 界面为什么是 Material Design？ | 只换皮肤不换框架：一个 css 加 14 个模板，全部离线内置，没有构建步骤，46 条测试零影响。 |
| 权限为什么要放到数据库？ | 应用里的 if 只挡一条路径，换个人换条路径就绕过了；GRANT 是最后一道，且能审计。代价是表级授权没有行粒度，行级隔离仍靠应用 WHERE。 |

## 6. 出问题怎么办

| 现象 | 处理 |
|---|---|
| 服务起不来 | `cd project\sql` 跑 `99-rebuild.sql`，再 `cd ..\app; python app.py`；**还不行就只讲 PPT**——第 8/9/10 页的图就是备份 |

| 图表没出来 | 刷新一次；还白就说"数据在下面的表里"，指表格继续 |

| **报损失败（409）** | "结存不够了，换一种原料"。别现场改数字 |
