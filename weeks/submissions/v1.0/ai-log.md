## 3. AI 在业务判断上出错、被人工纠正的案例

> 只收录**影响业务口径 / 数据结论**的错误。纯技术性事故（编码、模板语法、截图时序等）不影响结论，
> 已在 `harness/issues/015` 与各周周报中记录，此处不重复。

| # | AI 的说法 / 做法 | 人工怎么发现的 | 纠正结果 |
|---|---|---|---|
| **3-1** | 说"字段列数是 121"，同一轮又说"161" | 两次数字对不上，要求逐文件重数 | 改用**括号感知解析**得 **132 列**（v0.1 提交点口径），成为"17 表 / 132 字段"这个基准 |
| **3-2** | 断言"`weeks/week01` 从未记录过第 2 周的修正"，并称之为**新发现** | 要求先检索再断言 | `weeks/week02/issue-review.md` §十 早就登记了 16 条 → 改写为「**已决修正未被反向同步**」，并据此补齐 week01 的 16 条 ⛔ 提示 |
| **3-3** | 直接用「14 BCNF + 3 反规范化」写 v1.0 文档 | 与 18 表的新口径核对 | 现行口径是 **15 张纯净 BCNF + 3 张受控冗余**（14+3 是 17 表时代的旧口径） |
| **3-4** | 把「补货预警」的门槛判成"低于补货点"，把 55 条"库存健康"的原料也算进去 | 预警页 60 行里大半根本不该出现，且预警列还是空的 | 补 `WHERE alert_priority < 5`，预警列改取 `alert_level`（索引 9），只剩 **5 条**：严重不足 2 / 触及补货点 2 / 人工沽清 1 |
| **3-5** | 用「商品 × 杯型 × 糖度」判配方覆盖率，结论是几十个组合"没有配方" | 与文档「58 组合只 55 有」矛盾 | **糖度不是覆盖维度**（无糖本就不耗糖类原料），该判法语义不成立 → 该图**判定为不可靠、不发布**，改用销量榜；A13 只以文字说明 |
| **3-6** | 起草约束「支付状态非空 ⇒ `pay_time` 非空」 | 全量核对发现 **37 单** `pay_status` 非空而 `pay_time` 为空 | 取消/弃单本就没有支付时间 → 只保留「`pay_time` 非空 ⇒ 支付状态非空」与「完成时间不早于支付时间」两条 |

> **纪律**：AI 的产出只有两种状态 —— **能被命令复算的，和不算证据的**。

## 5. 提示词是怎么记录的

本阶段同样采用**长 Agent 会话 + 结构化提炼**，而不是逐条粘贴对话：

| 环节 | 做法 |
|---|---|
| 固定开场 | `harness/prompts/agent-session-start.md`（开工对齐 SOP） |
| 需求来源 | 用户直接发指令；每次由 AI 先给**方案选项 + 代价**，用户拍板 |
| 记录落点 | 周报（`weeks/week05`—`week07`）+ Issue 文档（`harness/issues/011`—`015`）+ 本文档 |
| 验证证据 | `project/tests/`（14 项回归 + 41 条应用测试 + 三份基线）、`weeks/submissions/v1.0/result/`（30 组截图） |

> **提示词不可追溯的部分如实说明**：本阶段的对话是连续长会话，
> 本文档记录的是**每次任务的目标、AI 给的关键输出、以及人工改了什么**，
> 而不是逐字复刻的 prompt。判断依据是最终产物能否被命令复算（见 §3 末的纪律）。
